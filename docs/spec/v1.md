# tnl v1 spec

The hand-off spec for tnl 1.0: a self-hosted Edge and Outposts that expose Services behind NAT at public Hostnames over HTTPS. It is the destination of [Map: tnl v1, self-hosted tunnels from Caddy and WireGuard][map].

**How to read it.** Every contract is stated here in its final form, with later amendments already merged. Reasons, rejected options and checked facts are not repeated: they stay in the [ADRs](../adr/) and in the tickets linked from each section. Terms follow [`GLOSSARY.md`](../../GLOSSARY.md).

**Until 1.0.** Byte encodings and port numbers marked _(slice N)_ are chosen by the [slice](#12-build-order) that first builds them and written back here. Everything on the wire freezes at 1.0.0 ([ADR 0008][adr8]).

## 1. Scope

**v1 does:**
- One operator, one Edge on a Linux VPS with a public IPv4 address, and many Outposts.
- Outposts dial out only, and run without root, a TUN device or a kernel module.
- Public Hostnames in the operator's Zones get automatic HTTPS: one certificate per Hostname, or one wildcard per Zone through Cloudflare DNS.
- HTTP and HTTPS Services anywhere on an Outpost's network.
- Server-Sent Events streams held open for hours, unbuffered, and uploads up to 250 MB.
- Routes managed with `tnl route` on the Edge host or an Outpost, or declared in an Outpost's settings.
- Zones and Outposts managed with `tnl zone` and `tnl outpost` on the Edge host, or declared in the Edge's settings, so that one Compose file on the Edge and one on each Outpost hold the whole setup.

**v1 doesn't:** anything in the map's [Out of scope][map] section. That includes several Edges, WebSockets held across Caddy reloads, wildcard Routes, several Outposts per Hostname, networks that block UDP, access control, raw TCP or UDP, a web UI, metrics and notifications.

## 2. Architecture

```
                     ┌────────────────── Edge: tnl edge ──────────────────┐
Visitor ── HTTPS ──▶ │ Caddy (embedded)                                   │
  h1, h2: TCP 443    │   tnl router: looks up the Hostname per request    │
  h3:     UDP 443    │     reverse_proxy ▶ tnl transport ▶ netstack ▶ WG ─┼── UDP 51820 ─┐
                     │ state store (state.json)                           │              │
                     │ API on tnl.sock and on 100.64.0.1 in the Tunnel    │              │
                     └────────────────────────────────────────────────────┘              │
                                                                                Tunnel   │
                     ┌──────────────── Outpost: tnl connect ──────────────┐              │
Service ◀── TCP ──── │ forwarder ◀ netstack ◀ WG ◀────────────────────────┼──────────────┘
  host's network     │ pinger, relay (tnl.sock), Declaration              │
                     └────────────────────────────────────────────────────┘
```

- **The Edge** terminates HTTPS for every Hostname and looks up each request's Route in tnl's own table, never in Caddy's config. It dials the Route's Outpost through userspace WireGuard inside its own process, and names the Service in a tnl header on each connection ([ADR 0001][adr1], [ADR 0002][adr2]).
- **An Outpost** holds no Route table. It reads the header, checks its optional allowlist, dials the Service on its host's network and copies bytes. It never parses HTTP, and for `https://` Services TLS runs from the Edge to the Service.
- **Both sides use userspace WireGuard** (`wireguard-go` on gVisor's netstack). Neither needs `CAP_NET_ADMIN` or a `wg0` interface. The Edge needs only `CAP_NET_BIND_SERVICE`, to bind ports 80 and 443.
- **Tunnel addresses** come from `100.64.0.0/10`, which isn't configurable. The Edge is `100.64.0.1`. An Outpost added with `tnl outpost add` gets the next /32, and a declared Outpost's is derived from its name. They exist only inside the two netstacks, so they can't clash with any host or LAN address.
- **There is no persistent control channel.** Joining, Route management and Declarations are calls to the Edge's API inside the Tunnel. Liveness and versions ride a small UDP ping.
- **One command, two builds.** The full build (about 55 MB) runs either role. The Outpost-only build (about 9 MB, selected by a build tag) leaves out Caddy and every Edge command.
- **Stack:** Go 1.27 or newer, and Caddy v2.11.7 or newer, pinned to an exact version in `go.mod`, plus `wireguard-go` and gVisor's netstack. It builds with plain `go build -tags nomysql`, with no cgo and no xcaddy. The module is `github.com/hyprsh/tnl`.
- **Licence:** Apache-2.0. Copied files keep their original notices, and `NOTICE` credits `wireguard-go` (MIT) and any Tailscale code (BSD-3). Pangolin, Newt and Gerbil are AGPL-3.0: they are read as evidence and never copied.

## 3. Components

### The Edge

- **State store.** Holds the state in memory and is its only writer. Every change takes one lock, whether it comes from the CLI, an Outpost or a join. Under the lock the store:
  1. checks the change against the current state
  2. saves it: write `state.json.tmp`, fsync it, rename it over `state.json`, fsync the directory
  3. swaps the new snapshot into what requests read

  Requests read snapshots and never wait on the lock. If a save fails, the command fails and nothing changes live. Slow follow-ups run after the lock is released: certificate waits, test dials, Caddy reloads, peer changes and closing connections. See [state.json](#statejson).
- **API.** One set of HTTP/1.1 + JSON handlers, served on two listeners:
  - `tnl.sock` in the state directory: the caller is `local`, with full rights.
  - `100.64.0.1:7001` (the API port) inside the Tunnel: the caller is `outpost:<name>`, taken from the Tunnel source address, with Outpost rights.

  The listener sets the actor, and the actor sets both the rights and the `actor=` field in the logs. See [Tunnel API](#tunnel-api).
- **Caddy config builder.** Builds Caddy's JSON from `state.json` and the startup flags, and loads it with `caddy.Load`. It runs at every start and on every wildcard Zone change. Caddy's config holds only the servers, the logging, and the TLS automation: one policy per wildcard Zone that names the Zone, and the Route Hostnames whose certificates the certificate manager holds, so a reload keeps them. It holds no Routes, meaning no Outposts and no Services, and no tokens ([ADR 0002][adr2], [ADR 0005][adr5]). Adding, removing or changing a Route never reloads Caddy.
- **Router**, a tnl HTTP handler module. Looks up the request's Hostname in the current snapshot, decides from the Outpost's state whether to proxy the request or answer it itself, and hands proxied requests to Caddy's `reverse_proxy`.
- **Transport**, a tnl module in `http.reverse_proxy.transport` that is its own `http.RoundTripper`. Dials the Outpost's Tunnel address through netstack, writes the tnl header, reads the reply and retries dial errors. Then it speaks HTTP/1.1 to the Service, over TLS for `https://` Services.
- **Permission module** (`tls.permission`). Allows on-demand issuance only for Hostnames that have a Route. Its refusal wraps `caddytls.ErrPermissionDenied`, so a scanner's SNI is logged at `debug` only.
- **DNS provider module** (`dns.providers`). When a DNS-01 challenge runs, reads the Zone's provider and current token from the state and calls that provider's libdns package. Providers are compiled in. v1 has Cloudflare (`libdns/cloudflare`). Adding Hetzner later (`libdns/hetzner/v2`) is an import, an entry naming its credential fields, and a release.
- **Certificate manager.** Hands every Route Hostname that no wildcard covers to Caddy's TLS app, under an automation policy that isn't on-demand, so it renews in the background. It does this after every Caddy load and every change to the Routes, and it stops renewing the Hostnames whose Route is gone, with no reload: Caddy has no call for that, so the names get a policy of their own, ahead of the one that manages them, that is on-demand, and certmagic's maintenance loop skips every on-demand certificate. The certificate it holds serves until it expires. It waits for certificates on `route add` and `zone add`, and subscribes to `cert_obtained` and `cert_failed` through Caddy's events app. Its event handler only records and returns, because it runs on the emitting goroutine.
- **Log core**, a `caddy.logging.cores` module on Caddy's `default` log, whose writer is `discard`. A zap→slog adapter that tnl writes itself turns Caddy's entries into tnl lines, using the level map in [Caddy and wireguard-go](#caddy-and-wireguard-go).
- **Tunnel.** `wireguard-go` with one peer per Outpost, on tnl's own netstack device. The device is copied from `wireguard-go`'s MIT-licensed `tun/netstack` (about 150 lines) so that tnl holds the gVisor stack. Every Tunnel connection gets TCP keepalive.
- **Liveness.** Answers pings and records when each Outpost was last heard from and which version it runs. It decides whether an Outpost is online, Offline or Incompatible, and closes an Outpost's connections when it goes Offline.
- **Connection tracker.** Knows every proxied connection by Route and by Outpost. So editing or removing a Route, removing an Outpost or losing one closes exactly its connections, and SIGTERM can drain.
- **Error responder.** Serves the error page and its plain-text form, and answers event-stream requests with a `retry:` field ([ADR 0013][adr13]).
- **Backup.** Writes the `tnl backup` archive.

### An Outpost

- **Tunnel.** `wireguard-go` on the same netstack device, with one peer, the Edge, and `persistent_keepalive_interval = 25`.
- **Forwarder.** Listens on its Tunnel address at the data port, 7000. For each connection it reads the tnl header, checks the allowlist, dials the Service with the host's resolver and network, replies, and then copies bytes both ways.
- **Pinger.** Pings the Edge every 10 s and tracks its answers. After 30 s without an answer it re-resolves the Edge's address. It sends the Declaration when the Edge's copy differs.
- **Relay.** The Outpost's `tnl.sock`. Forwards the local CLI's API calls to the Edge unchanged, and answers `status` and `info` itself. Each attempt to reach the Edge's API waits 5 s; when it fails, the relay answers 503 "Outpost not connected". It logs Route changes made through it at `info`.
- **State.** The Outpost's state directory, written when it joins. An Outpost with an Outpost credential writes no state.

### The CLI

The CLI is a client of the socket of whichever process runs on the host. It:
1. finds the socket ([State directories and sockets](#state-directories-and-sockets))
2. asks the process for its role, version and build
3. refuses unless that version is exactly its own: "this `tnl` is 1.4.2 but the running Outpost is 1.4.1; restart it (`sudo systemctl restart tnl-outpost`)"
4. sends the command

The role tells `tnl route` whether it needs `--outpost`.

## 4. Protocols

Sources: [Joining][t6], [Route management][t7], [Version skew][t15], [Reconnects][t14], [Routes declared on the Outpost][t17], [Declaring the Edge's Zones and Outposts][t28].

### Versions

- **SemVer.** From 1.0.0, an Edge accepts Outposts of its own major whichever side is newer, plus Outposts of the previous major ([ADR 0008][adr8]). Before 1.0, two versions work together only when they share the minor: `0.3.1` works with `0.3.4`, never with `0.4.0`.
- **The Edge is the judge.** It learns each Outpost's version from the ping. An Outpost refuses only an Edge of an older major: in a join token (before touching its state), and later when a ping answer shows one, when it logs `error` naming both versions once per Edge version, keeps running and keeps pinging, and so recovers when the Edge is upgraded or rolled forward (an Outpost never exits on its own). When the Edge's answer says the Outpost is outside the window, the Outpost keeps running and logs `warn` once per Edge version.
- **A join token the Outpost can't use** is one from an Edge of an older major, or from an Edge whose window doesn't take this Outpost. The Outpost to install is the Edge's own version, which always works.
- **On one host, the CLI and the running process must be the exact same version.**
- **A version that isn't SemVer,** such as `dev`, is never judged: no side calls it outside the window.
- **Where the rules live:** one Go package, `internal/version`, holds the window, what an Outpost accepts of an Edge, the compatibility line and the wording of every version-aware refusal.
- **The Edge knows only that a field is unknown.** Which version added a field is known to the newer side, so the client composes "it needs 1.5 or newer" from its table of fields added after 1.0 (`api.FieldAdded`, empty in v1), using the Edge's `Tnl-Version`. The Edge's own message says "it needs a newer version". It names the field in a `Tnl-Unknown-Field` response header, not in the body, because a body field would be one more thing an older client refuses.
- **Changes within a major are additive only,** and both sides refuse fields they don't know, on every surface:
  - the API (except that a client reads the `ls` and status replies and an Outpost's own Routes leniently: see [Status](#status) and [ADR 0012][adr12]), the tnl header and the ping
  - the Declaration and `TNL_*` variables
  - state files

  Every refusal names both versions and which side to upgrade.
- **The next major's Edge must keep speaking** the previous major's tnl header and reply, ping, join token and API.

### Join token

- **It carries:**
  - a `tnl1` marker
  - the Edge's `--address` and WireGuard port
  - the Edge's WireGuard public key
  - the one-time private key
  - the Outpost's Tunnel address
  - the Edge's version

- **Encoding:** `tnl1.` followed by the unpadded base64url (RFC 4648 §5) of one JSON object, so a token is a single shell-safe word. The object has exactly these keys, and a reader refuses any other:

  | Key | Holds |
  |---|---|
  | `a` | the Edge's `--address`, a DNS name or an IP |
  | `p` | the Edge's WireGuard port, an integer |
  | `k` | the Edge's WireGuard public key, standard base64 as in `wg` |
  | `o` | the one-time WireGuard private key, standard base64 |
  | `t` | the Outpost's Tunnel address, such as `100.64.0.2` |
  | `v` | the Edge's version |

  The Outpost keeps the SHA-256 of the token text, trimmed of surrounding whitespace, in its state.
- **The Tunnel address is in the token** because WireGuard drops packets whose inner source isn't the peer's allowed address, so the Outpost needs it before it sends its first packet. Everything else, the Outpost's name included, comes back in the join exchange.
- **It works once and expires,** after 1 h by default (`--ttl`). The Edge never stores it.
- **Its format should never change.** New fields go into the join exchange. If the format ever must change, the Edge keeps minting the old one for the previous major.
- **An Outpost refuses a token it can't use** before touching its state, naming the Edge's version and the Outpost version to install. An unknown marker means a newer tnl is needed.

### Outpost credential

- **It carries:**
  - a `tnlc1` marker
  - the Outpost's name
  - the Edge's `--address` and WireGuard port
  - the Edge's WireGuard public key
  - the Outpost's WireGuard private key
  - the Outpost's Tunnel address

- **Encoding:** `tnlc1.` followed by the unpadded base64url (RFC 4648 §5) of one JSON object, as for the join token. The object has exactly these keys, and a reader refuses any other:

  | Key | Holds |
  |---|---|
  | `n` | the Outpost's name |
  | `a` | the Edge's `--address`, a DNS name or an IP |
  | `p` | the Edge's WireGuard port, an integer |
  | `k` | the Edge's WireGuard public key, standard base64 as in `wg` |
  | `o` | the Outpost's WireGuard private key, standard base64 |
  | `t` | the Outpost's Tunnel address, derived from its name |

- **It is minted offline** by `tnl credential`, which never contacts an Edge, so it carries no Edge version ([Declared Zones and Outposts](#declared-zones-and-outposts)).
- **It is the Outpost's identity and never expires.** Anyone holding it connects as that Outpost until the Edge's line for it changes ([ADR 0010][adr10]).
- **The Tunnel address is derived from the name** by a fixed hash into `100.64.0.0/10` that never yields `100.64.0.0`, `100.64.0.1` or `100.127.255.255`. The Edge derives it from the declared name, and `tnl credential` writes it into `t`.
- **The hash:** take the first 8 bytes of the SHA-256 of the name's UTF-8 bytes as a big-endian unsigned integer `h`. The address is `100.64.0.0` plus `h mod (2^22 - 3) + 2`. That is an offset from 2 to 2^22 - 2, so the three reserved addresses are never produced. `nas` derives `100.85.233.86`, `laptop` `100.69.25.55`, `a` `100.90.148.130`.
- **Its format and the hash should never change.** If either ever must, `tnl connect` keeps reading the old credential for the previous major.

### Join exchange

1. `tnl connect --token` brings the Tunnel up with the one-time key and the token's Tunnel address, and generates the Outpost's own key pair.
2. It calls the Edge's API at `100.64.0.1` with its new public key and its version.
3. Under the lock, the Edge checks that the peer hasn't joined yet and that the token hasn't expired. It swaps the peer's key, forgets the one-time key, and answers with the Outpost's name and the Edge's version.
4. The Outpost writes its state ([Outpost state](#outpost-state)) and switches to its own key.

The Outpost's private key never leaves its machine ([ADR 0003][adr3]). A declared Outpost doesn't join: it connects with its [Outpost credential](#outpost-credential) from the first packet.

### Tunnel API

- **HTTP/1.1 + JSON over TCP,** with the same handlers on `tnl.sock` and on `100.64.0.1:7001`, the API port. The listener exists only in the Edge's netstack, so nothing listens on a host address. A request from a Tunnel address that belongs to no Outpost is refused with 403.
- **Paths,** all under `/v1`, with JSON bodies. Later slices add their paths here:

  | Method and path | Does | Slice |
  |---|---|---|
  | `GET /v1/info` | the process's role, version, build (`full` or `outpost`) and VCS revision | 1 |
  | `GET /v1/zones` | lists Zones, sorted by name; never a token; each with `declared` and its certificate (`certificate` for a wildcard Zone, `certificates` for a per-Hostname one), as [Status](#status) shows | 1, certificates 10 |
  | `POST /v1/zones` | adds a Zone; body `{"name": "example.com"}`, plus `"provider"` and `"token"` for a wildcard Zone; answers the Zone, for a wildcard Zone its `dns_zone` and `covers`, `served`, and any `warnings` | 1 |
  | `GET /v1/routes` | lists Routes and waiting lines, sorted by Hostname, the Route before the line that waits; each with its `status`, and `waiting` (the reason) on a line that waits | 1, status 10 |
  | `POST /v1/zones/edit` | changes a Zone's certificate mode or token; body `{"name"}` plus exactly one of `"wildcard"` (a provider, with `"token"`: switch to wildcard), `"per_hostname": true` (switch back, deleting the token) or `"token"` alone (replace a wildcard Zone's token); the token is checked as at `zone add` and a refused one changes nothing; answers `{"name", "mode", "provider", "dns_zone", "covers"}` and any `warnings`; 404 for an unknown name, 409 for a switch to the mode the Zone is in or a token for a per-Hostname Zone, 400 for none or several changes; `local` only | 5 |
  | `POST /v1/zones/rm` | removes a Zone; body `{"name", "with_routes"}` (`with_routes` optional); answers `{"name", "removed", "moved"}`, the Hostnames of the Routes removed with it and of those a parent Zone took over, with `waiting` naming the declared ones among the removed, which wait again, `served`, and any `warnings`; 409 listing the Routes that no other Zone contains if `with_routes` is off, 404 for an unknown name; `local` only | 5 |
  | `POST /v1/routes` | adds a Route; body `{"hostname", "service", "outpost", "host_header", "insecure_skip_verify"}`, the last two optional; answers the Route, with `warnings` for a Hostname that doesn't point at the Edge or a certificate that isn't there after about 60 s, and for the [test dial](#routes)'s findings | 1, test dial 4 |
  | `POST /v1/routes/edit` | changes a Route and closes its connections, even when only an option changed; body `{"hostname"}` plus any of `"service"`, `"outpost"`, `"host_header"` (`""` clears it) and `"insecure_skip_verify"`, left alone when absent; answers the Route and any `warnings` (a changed `"service"` is test-dialed); an Outpost may change only its own Routes (403 naming the holder otherwise, and for naming another Outpost); 404 for an unknown Hostname, 400 for nothing to change | 4 |
  | `POST /v1/routes/rm` | removes a Route and closes its connections; body `{"hostname"}`; answers the removed Route, `served` and any `warnings`; an Outpost may remove only its own Routes (403 naming the holder otherwise); 404 for an unknown Hostname | 4 |
  | `GET /v1/outposts` | lists Outposts, sorted by name, with their state, last seen, endpoint, version, Tunnel address and Route counts, as [Status](#status) shows; `local` only | 10 |
  | `GET /v1/status` | the process's own status, tagged by `role`; the Edge answers its summary and its Needs attention list, as [Status](#status) shows; `local` only | 10 |
  | `POST /v1/outposts` | adds an Outpost; body `{"name": "laptop", "ttl": "1h"}` (`ttl` optional, a Go duration, 1 h by default); answers `{"name", "address", "token"}` | 1, `ttl` 3 |
  | `POST /v1/outposts/rm` | removes an Outpost; body `{"name", "with_routes"}` (`with_routes` optional); answers `{"name", "routes"}`, the Hostnames of the Routes removed with it, `served`, and any `warnings`; 409 listing the Routes if some point at it and `with_routes` is off, 404 for an unknown name; `local` only | 3 |
  | `POST /v1/outposts/rekey` | revokes the Outpost's key at once and mints a new token; body `{"name", "ttl"}` (`ttl` as for add); answers like `POST /v1/outposts`; `local` only | 3 |
  | `POST /v1/join` | the join exchange; body `{"public_key", "version"}`; answers `{"name", "edge_version"}`; 403 once the Outpost has joined or its token has expired, and for every Outpost while the Edge declares its Outposts | 3 |
  | `POST /v1/declaration` | the Outpost sends its whole Declaration, even an empty one; body `{"routes": [{"hostname", "service", "host_header", "insecure_skip_verify"}]}`, the last two optional, with the Hostname lower-case and the Service in its canonical form; answers `{"lines": [{"hostname", "outcome", "reason"}], "removed", "switched"}`, `served` and any `warnings` (`outcome` is `added`, `changed`, `unchanged` or `waiting`, with `reason` for a waiting line; `removed` names the lines that are gone and `switched` the Routes made with the CLI that the Declaration replaced); 400 for a bad line, a Hostname twice or a form that isn't canonical, changing nothing; `outpost:<name>` only | 8 |
  | `GET /v1/declaration` | the Outpost's own Routes and waiting lines as the Edge has them; answers `{"routes": [{"hostname", "service", "host_header", "insecure_skip_verify", "waiting", "wait_kind", "reason", "holder"}]}`, sorted by Hostname, with `waiting`, `wait_kind` (`held`, `outside_zone` or `not_applied`; the Outpost words it, so it needn't read `reason`) and `reason` (the Edge's log wording) only for a waiting line, and `holder` (the Outpost holding the Hostname) only where that is why it waits; `outpost:<name>` only | 8 |
  | `GET /v1/logs` | streams the process's own recent log lines from its ring, as [Logs](#logs) describes; `text/plain`, one line per log line, flushed as it comes; query `n` (the last n lines), `since` (a Go duration), `level` (`error`, `warn`, `info` or `debug`: that level and above), `follow=1` (keep the reply open until the caller goes) and `format=json` (JSON lines whatever the process logs); 400 for a bad value; `local` only, and an Outpost's relay answers it itself with the Outpost's own ring instead of forwarding it | 10 |
  | `GET /v1/backup` | streams the backup tar (`application/x-tar`); `local` only. Certificates left out are named in `Tnl-Backup-Skipped` headers, one per certificate, sent before the body | 9 |

  A refusal is an HTTP status of 400 or above with the body `{"error": "<message>"}`: 400 for an invalid request, 403 for a caller without the right, 409 for a name already taken.
- **Warnings:** a reply that changes state may carry `"warnings": ["<message>", ...]`, an array of strings left out when empty. The change is made either way. The CLI prints each to stderr as `warning: <message>` and exits 0. The Edge logs the same string at `warn` with the actor, after the lock is released. In Go, a reply type embeds `api.Warnings`. `zone add` is the first user: after saving, for a wildcard Zone it resolves a random name under it and warns if that name doesn't point at the Edge's `--address`. `route add` and `route edit` follow it with the test dial's warnings.
- **Handovers:** a reply to a change that can free a Hostname or add a Zone (`route rm`, `outpost rm`, `zone add`, `zone rm` and a Declaration) may carry `"served": [{"outpost", "hostname"}]`, left out when empty: the waiting lines that the change turned into Routes. The CLI prints "newbox declared photos.example.com and now serves it" for each. In Go, a reply type embeds `api.Handovers`.
- **The CLI finds `tnl.sock`** as described in [State directories and sockets](#state-directories-and-sockets). With nothing listening it exits 1 with "no Edge or Outpost is running".
- **Every request and response carries `Tnl-Version: <semver>`.**
- **A request with an unknown field is refused whole:** "the Edge (1.4.2) doesn't support `--new-opt`; it needs 1.5 or newer; upgrade the Edge".
- **Calls from an Incompatible Outpost are refused** with 403: "the Edge (2.0.0) doesn't accept this Outpost (0.9.1); upgrade the Outpost". It says "upgrade the Edge" when the Outpost is the newer side. The refusals are not logged: the Edge's `warn` for the version change is the one line.
- **Route options that need a newer Outpost** than the Route's are refused at `route add` and `route edit`, naming the version needed. v1 has none.

**Rights:**

| Operation | `local` (the Edge host) | `outpost:<name>` |
|---|---|---|
| join | – | its own, while not joined |
| `outpost add`, `rm`, `rekey`, `ls` | yes | no |
| `route ls` | every Route and waiting line | every Route and waiting line |
| `route add`, `edit`, `rm` | any Route; `--outpost` chooses the Outpost | only Routes through itself, never onto another Outpost |
| `zone add`, `edit`, `rm` | yes | no |
| `zone ls` | yes | yes |
| send its Declaration; fetch its Routes and waiting lines | – | its own |
| `backup`, Edge `status`, `logs` | yes | no |

While an Outpost declares, `route add`, `edit` and `rm` are refused for its Routes from both callers. That includes moving a Route onto it or off it.

While the Edge declares its Zones, `zone add`, `edit` and `rm` are refused with status 409: "Zones are declared; change TNL_ZONE_* and restart the Edge". While it declares its Outposts, `outpost add`, `rekey` and `rm` are refused the same way ("Outposts are declared; change TNL_OUTPOST_* and restart the Edge"), and no Outpost joins ([Declared Zones and Outposts](#declared-zones-and-outposts)). An Outpost caller gets the usual 403 first, as these commands are `local` only.

### tnl header and reply

Each Tunnel connection from the Edge to `<outpost-address>:7000`, the data port, starts with the tnl header:
- a fixed marker and a format number, always first
- the Service's `host:port`
- the Route's Hostname, for the Outpost's logs
- the request ID

The Outpost replies before any request byte is sent, with one of:
- **ok:** both sides then copy bytes.
- **dial error,** with a reason: `refused`, `timeout`, `dns` or `allowlist`.
- **unsupported,** with the Outpost's version. This reply never changes across majors, so a mismatch is always reported, never misparsed.

The Edge picks the header format from the Outpost's version (`wire.FormatFor`; only format 1 exists, so every version gets it) and never sends a field that version lacks. The Outpost refuses any field it doesn't know.

**Encoding.** All numbers are unsigned. The data port is **7000**. It exists only inside the Tunnel, so no host port can clash with it.

The header is:

| Part | Bytes |
|---|---|
| marker | `74 6e 6c 00` (`tnl` and a zero byte) |
| format number | one byte, `1` |
| fields, in any order, each at most once | tag byte, length as a uvarint, then that many bytes |
| end | tag `0` |

| Tag | Field | Longest |
|---|---|---|
| `1` | the Service's `host:port`, required | 255 bytes |
| `2` | the Hostname | 255 bytes |
| `3` | the request ID | 64 bytes |

The Outpost refuses an unknown marker, an unknown format number, an unknown or repeated tag, an over-long field or a missing Service. It reads the whole header within 10 s, then dials the Service within 5 s.

The reply has no marker or format number, so it can be read the same way across majors:

| Reply | Bytes |
|---|---|
| ok | `00` |
| dial error | `01`, then the reason: `01` refused, `02` timeout, `03` dns, `04` allowlist |
| unsupported | `02`, then one length byte and the Outpost's version as text |

The Outpost sends **unsupported** and closes the connection when it refuses a header. It sends **dial error** with `refused` for any failure that isn't a timeout or a DNS error, an unreachable network included. It sends nothing when the header doesn't arrive in time.

### Ping

A small tnl UDP message inside the Tunnel, on port **7002** at both ends: the Edge listens on `100.64.0.1:7002`, and the Outpost sends from its own Tunnel address, port 7002, and reads the answer on the same socket. Like the data port, it exists only inside the netstacks, so no host port can clash with it.

**Encoding.** One datagram, with the tnl header's layout and numbers as in [the header](#tnl-header-and-reply):

| Part | Bytes |
|---|---|
| marker | `74 6e 6c 01` for the ping, `74 6e 6c 02` for the answer |
| format number | one byte, `1` |
| fields, each at most once | tag byte, length as a uvarint, then that many bytes |
| end | tag `0` |

| Tag | Field | Longest |
|---|---|---|
| `1` | the sender's version as text, required | 64 bytes |
| `2` | in the answer only: whether the Outpost is inside the Edge's window, one byte, `1` inside or `0` outside; an answer without it counts as inside | 1 byte |
| `3` | in the ping: the digest of the Outpost's Declaration | 32 bytes |
| `4` | in the answer: `1` if the ping's digest matches the Edge's stored copy, else `0`; it comes with tag `5` | 1 byte |
| `5` | in the answer: the digest of this Outpost's Routes and waiting lines as the Edge has them; it comes with tag `4` | 32 bytes |

A ping without tag `3` is answered without tags `4` and `5`, as the Edge's own ping at start is, and an answer without them tells the Outpost nothing about its Declaration. A digest of the wrong length, a flag other than `0` or `1`, tags `4` and `5` apart, and tag `3` in an answer or tags `2`, `4` and `5` in a ping are refused like any unknown, over-long or repeated field.

The markers differ from each other and from the header's, so no message is taken for another. A receiver refuses an unknown marker, an unknown format number, an unknown or repeated tag, an over-long field, a missing version, a cut-short datagram and bytes after the end. The Edge drops what it refuses without an answer, and drops a datagram from a Tunnel address that belongs to no Outpost.

- **The digests** are SHA-256 over a canonical text built from the parsed lines, so they don't depend on JSON key order, whitespace or the order of lines:
  - The Declaration's digest is over `tnl-declaration-1`, a newline, then for each line in Hostname order its Hostname, Service URL (canonical), host header (empty if none) and `1` or `0` for `insecure_skip_verify`, each followed by a NUL byte, and a newline. An empty Declaration is the digest of the prefix alone.
  - The digest of the Outpost's Routes and waiting lines is over `tnl-routes-1` and a newline, then the same record for each of its Routes and waiting lines in Hostname order, with a further field `applied` or `waiting` before the newline. It covers Routes made with the CLI as well.
- **The Outpost pings `100.64.0.1` every 10 s.** The ping carries a marker and format number, the Outpost's version, and the digest of its Declaration. An empty Declaration has a digest too.
- **The Edge answers** with:
  - its version
  - whether the Outpost is inside its window
  - whether the Declaration's digest matches the Edge's stored copy
  - a digest of this Outpost's Routes and waiting lines as the Edge has them
- **At start, the Edge pings every remembered endpoint.** That ping is also its first handshake, so the Edge knows every online Outpost's version within one round trip. The Edge's ping is the same datagram as an Outpost's, sent from `100.64.0.1:7002` to the Outpost's Tunnel address on port 7002; the Outpost answers it at once with a ping of its own.
- **Anything from an Outpost counts as hearing from it:** a ping or any data packet.
- **Versions are runtime facts** and are never saved.

## 5. State and config

Sources: [Where the Edge keeps its state][t11], [Packaging][t13], [Joining][t6], [Routes declared on the Outpost][t17], [Declaring the Edge's Zones and Outposts][t28].

### The Edge's state directory

`--state-dir` (`TNL_STATE_DIR`), default `/var/lib/tnl`. The directory is mode 0700 and its files 0600, owned by the user the Edge runs as. The whole directory is secret, and so is every backup of it. There is no encryption at rest, because the key would sit on the same disk.

| Path | What it holds |
|---|---|
| `state.json` | everything the Edge must remember |
| `state.json.v<n>` | the file as it was before a migration to a newer schema |
| `tnl.sock` | the API, for the CLI on the Edge host |
| `caddy/` | Caddy's storage root and data directory: certificates, the ACME account key, `instance.uuid` |

### state.json

One JSON document with a schema `version` ([ADR 0006][adr6]). It holds:
- **the Edge's WireGuard private key,** which must match `--key-file` or `TNL_KEY` when either is set
- **the next-Tunnel-address counter:** `.2`, `.3` and so on, for Outposts added with `tnl outpost add`. It skips addresses that are taken, and its addresses are never reused after removal.
- **Outposts:**
  - name, WireGuard public key and Tunnel address, and whether it is declared
  - the last WireGuard endpoint, written whenever it changes
  - for an Outpost that hasn't joined, or was rekeyed and hasn't joined again: the one-time public key and the token's expiry
- **Declarations:** for each Outpost that declares, its lines (Hostname, Service URL, options), each with the time it was first declared. A line is a Route when Routes holds its Hostname through that Outpost, and waits otherwise, so no waiting flag is stored. A line that stays in a Declaration keeps its time. The key is `declarations` and is absent while no Outpost declares. The declared marks (`declared`, on Zones and Outposts) came with schema version 2, so the Edge refuses a version 1 file.
- **Routes:** Hostname, Outpost, Service URL, `insecure_skip_verify` and `host_header`. A Route doesn't store its Zone, which is worked out from the Hostname.
- **Zones:** name and mode (`per-hostname` or `wildcard`), plus the DNS provider and token for a wildcard Zone, and whether it is declared

**Never saved:** join tokens, when an Outpost was last heard from, versions, handshakes, open connections and certificate status. Caddy keeps the certificates themselves in `caddy/`.

**Rules:**
- **Only the running Edge writes it.** The CLI never touches it. Before each save the Edge checks that the file still holds exactly what it last wrote. If not, it refuses the change: "state.json was changed outside tnl; restart the Edge to load it". Hand edits are made with the Edge stopped.
- **It is checked whole at start.** The Edge refuses to start, naming the bad entry, unless:
  - Hostnames are unique
  - every Route's Outpost exists
  - every Hostname is inside a Zone
  - every Declaration belongs to an Outpost, has valid lines with no Hostname twice, and holds every Route that Outpost has
  - Tunnel addresses are unique, and those the counter assigned are below it
  - keys parse
  - every wildcard Zone has a provider and a token
  - the key matches `--key-file` or `TNL_KEY`, when either is set: "state.json holds a different Edge key than TNL_KEY_FILE"

  It never loads part of the state and skips the rest.
- **Migrations:** before 1.0 there is no migration: a tnl refuses a `state.json` whose schema it doesn't know, older or newer. From 1.0, a newer tnl migrates the file on start and keeps the old one as `state.json.v<n>`, and an older tnl still refuses a schema it doesn't know. Downgrading means restoring the kept file.
- **First start:** an Edge that finds the directory missing or empty creates the state, with its WireGuard key taken from `--key-file` or `TNL_KEY`, or generated. It logs "no state in `<dir>`, created a new Edge" with the key's fingerprint. There is no init command.
- **Key fingerprint:** `SHA256:` and the unpadded base64 of the SHA-256 of the 32-byte WireGuard *public* key, as `ssh-keygen -l` prints. It is the `key_fingerprint` field in the logs and in `tnl status`. The private key is never logged. In `state.json`, keys are standard base64, as in `wg`.
- **A directory that has files but no `state.json`** is refused rather than treated as new, so a misplaced restore can't silently get a fresh key.
- **Everything else is built from it** at every start: WireGuard peers, the Route table and Caddy's config.

### Outpost state

**The directory** is `--state-dir` (`TNL_STATE_DIR`):
- **default:** `$XDG_STATE_HOME/tnl-outpost`, which is `~/.local/state/tnl-outpost`, on Linux and macOS alike
- **under systemd or Docker:** `/var/lib/tnl-outpost`, set by the unit and the image

It is mode 0700 and its files 0600.

- **`state.json`,** with a schema `version`. It holds:
  - the Outpost's WireGuard private key and Tunnel address, and its name, learned in the join exchange
  - the Edge's address, WireGuard port and public key
  - the SHA-256 of the token that created the state
- **The Outpost's `state.json` migrates from slice 7, before 1.0 too** (the Edge's does not, until 1.0): a newer tnl migrates an older schema on start, logs it at `info`, and keeps the old file as `state.json.v<n>`. An older tnl refuses a schema it doesn't know and leaves the file alone. When a migration cannot know a value, it uses a stand-in: schema 1 had no name, so the Outpost's Tunnel address stands in for it.
- **`tnl.sock`:** the relay.

**With an Outpost credential** (`--credential-file`, `TNL_CREDENTIAL_FILE` or `TNL_CREDENTIAL`), the Outpost writes no `state.json`. Everything comes from the credential, the directory holds only `tnl.sock`, and an Outpost container needs no volume. An existing `state.json` is left alone and ignored, with an `info` line.

**It holds no Routes.** If the token that created the state is passed again, as in a container restarting with `TNL_TOKEN` still set, it is ignored. A different token joins again and replaces the state.

### Startup settings

Settings are flags, and each has a `TNL_*` variable. Changing one takes a restart.

**`tnl edge`:**

| Flag | Variable | Default |
|---|---|---|
| `--address` | `TNL_ADDRESS` | Required. The DNS name Outposts dial; the help text recommends a name over an IP. |
| `--wireguard-port` | `TNL_WIREGUARD_PORT` | `51820`. Set to `443`, it switches HTTP/3 off with a log line. |
| `--acme-email` | `TNL_ACME_EMAIL` | none |
| `--acme-ca` | `TNL_ACME_CA` | Let's Encrypt production |
| `--key-file` | `TNL_KEY_FILE`, or `TNL_KEY` holding the key itself | none, so the Edge generates its key at first start |
| `--zone` (repeatable) | `TNL_ZONE_<LABEL>` | none |
| `--outpost` (repeatable) | `TNL_OUTPOST_<LABEL>` | none |
| `--state-dir` | `TNL_STATE_DIR` | `/var/lib/tnl` |
| `--log-level` | `TNL_LOG_LEVEL` | `info` |
| `--log-format` | `TNL_LOG_FORMAT` | `text`, or `json` |
| `--access-log` | `TNL_ACCESS_LOG` | off |

**`tnl connect`:**

| Flag | Variable | Default |
|---|---|---|
| `--token` | `TNL_TOKEN` | Needed only to join. |
| `--credential-file` | `TNL_CREDENTIAL_FILE`, or `TNL_CREDENTIAL` holding the credential itself | none |
| `--state-dir` | `TNL_STATE_DIR` | see [Outpost state](#outpost-state) |
| `--allow` | `TNL_ALLOW` | none, so the Outpost dials whatever the Edge names |
| `--route` (repeatable) | `TNL_ROUTE_<LABEL>` | none |
| `--log-level` | `TNL_LOG_LEVEL` | `info` |
| `--log-format` | `TNL_LOG_FORMAT` | `text` |

- **`--allow`** takes a comma-separated list, such as `192.168.1.0/24,localhost:3000`:
  - a CIDR matches the resolved address, on any port
  - a `host:port` matches the name and port exactly as the Edge sent them
- **`--route` and `TNL_ROUTE_*`** are described in [Declarations](#declarations). Setting both is refused.
- **`--zone`, `--outpost` and their variables** are described in [Declared Zones and Outposts](#declared-zones-and-outposts). Setting a flag and its variables together is refused. `tnl edge` refuses `TNL_ROUTE_*`: "Routes are declared on the Outpost; set TNL_ROUTE_* there".
- **Secrets** come from a file or a variable, never from a flag's value: the Edge's key, an Outpost credential, and a declared Zone's token. Setting both forms of one is refused. Every message that echoes a line or a variable redacts them, the "did you mean" included.
- **`--token` and an Outpost credential together** are refused.
- **Unknown `TNL_*` variables** stop `tnl edge` and `tnl connect` from starting, with a "did you mean".
- **A config error exits with code 78** (`EX_CONFIG`).

## 6. Behaviour

### A request

Sources: [Data path][t5], [Reconnects][t14], [Route management][t7].

1. **Caddy terminates TLS:** HTTP/1.1 and HTTP/2 on TCP 443, HTTP/3 on UDP 443. Port 80 answers ACME HTTP-01 challenges and redirects every other request to `https://` with a 308.
2. **The router looks up the Hostname.** If there is no Route, the answer is 404.
3. **It checks the Outpost.** An Offline or Incompatible Outpost gets 503 at once. For an online Outpost, or one the Edge has not heard from yet, the transport waits up to 10 s for the Tunnel, then fails with 503. A connect that hangs while the Tunnel is down is tried again every second within those 10 s, so a request goes through as soon as the Tunnel is back.
4. **The transport sends the tnl header.**
   - A `refused` or `dns` reply is retried every 250 ms until 5 s have passed since the first attempt.
   - A `timeout` reply (the Outpost's own dial timeout is 5 s) or an `allowlist` reply isn't retried.
   - When the retries run out, the answer is 502.

   Retrying is safe for uploads, because no request byte has been sent yet.
5. **On ok, the transport speaks HTTP/1.1 to the Service.**
   - An `https://` Service gets TLS, verified against the URL's host unless the Route has `--insecure-skip-verify`.
   - The Host header is the Visitor's, or the Route's `--host-header`.
   - Caddy's default `X-Forwarded-*` headers are passed on. The request ID isn't.
6. **Bodies stream unbuffered both ways,** and `text/event-stream` is flushed on every write. Whatever the Service answers passes through untouched, with two changes: the `Via` header Caddy adds (`1.1 Caddy`) is removed, and `Strict-Transport-Security: max-age=31536000` is added unless the Service sent its own (see [Security headers](#security-headers)). The Service's own `Server` header passes through; a Service that sends none gets none.

### Timeouts and Caddy settings

Sources: [Timeouts and buffering from visitor to Service][t10], [Uploads when a Service pauses reading][t12].

- **Caddy's servers:**

  | Setting | Value |
  |---|---|
  | `read_timeout`, `write_timeout` | 0 |
  | `read_header_timeout` | 1 min |
  | `idle_timeout` | 5 min |
  | `read_idle_timeout` | 5 min |
  | `write_idle_timeout` | 1 min |
  | `encode` | not used |
  | HTTP/3 | on |
- **Caddy as a whole:**
  - `grace_period` 0, so SSE streams survive any number of reloads
  - the admin endpoint off, and `admin.config.persist` false
  - storage and the data directory at `<state-dir>/caddy`, with the daily storage cleanup on
  - tnl's modules keep their shared state outside Caddy, because a reload cleans up the old config's modules while their streams still run
  - the TCP listeners are on a network of tnl's own (`tnltcp`) that keeps one socket per address across reloads. On Unix, Caddy's own `tcp` binds a new `SO_REUSEPORT` socket for each config and closes the old one after the new is up, and the kernel resets the connections still waiting in its accept queue. A reload hands the accepting to the new config and drops no connection that is waiting to be accepted. HTTP/3 is UDP and has no queue to reset
- **The transport:**
  - HTTP/1.1 only, with `DisableCompression`
  - no `ResponseHeaderTimeout`
  - `IdleConnTimeout` of about 90 s
  - idle connections pooled per Route
  - a `Cleanup` that drops only idle connections
- **The Tunnel:** netstack never times out an idle connection, and Nagle is off. The Outpost's forwarder sets deadlines only for reading the header (10 s) and dialling the Service (5 s).
- **Known limits:**
  - An upload fails if its Service stops reading for more than 5 min, over HTTP/2 only.
  - A Visitor that stalls an upload for more than 5 min fails on every protocol.
  - HTTP/2 uploads top out at about 1 MiB per round trip.
  - An HTTP/3 connection dies after 30 s of silence unless the client PINGs. A 20 s heartbeat keeps it alive.

### What Visitors see when the Edge answers

Source: [Reconnects][t14].

| Status | When | Message |
|---|---|---|
| 503 | the Outpost is Offline or Incompatible | "app.example.com is offline" |
| 502 | the Service is unreachable; the reason goes only to the log | "app.example.com isn't answering" |
| 404 | no Route for the Hostname | "Nothing is served at app.example.com" |

- **The page** is one built-in page, minimal and centred:
  - the status code, a thin vertical rule and the message
  - below that, in small muted text, the time and a short request ID that also appears in the log
  - inline CSS, no JS and no external requests
  - light or dark to match the Visitor's system setting

  Each carries the headers in [Security headers](#security-headers) and no `Server` header. It never names the Outpost, the Service's address, tnl or its version. Requests that don't accept HTML get one line of plain text. Every error carries `Cache-Control: no-store`. The page can't be customised in v1.
- **Event-stream requests,** whose `Accept` includes `text/event-stream`, never get the 502 or 503. A request that would get one is answered `200` with `Content-Type: text/event-stream`, `Cache-Control: no-store` and the body `retry: 5000\n\n`, and the stream is closed at once, so a browser waits 5 s before it asks again instead of several times a second. The log keeps the real status. A stream cut mid-way, as in [Lost closes](#liveness) below, ends without a `retry:` field, so the Service's own `retry:` or the browser's default applies. The reply is built in one place, so any header the Edge puts on its own replies goes on it ([ADR 0013][adr13], which amends [ADR 0007][adr7]).
- **Checked by hand, 2026-10-17** (#64, v0.1.0): Firefox, Chromium and Safari on macOS each kept retrying the reset through a 150 s outage and resumed with `Last-Event-ID` once the Outpost was back, so there was no need to answer `200` for the retry's sake. Browsers also retried the immediate reset several times a second once the Outpost was Offline (#84), which is why the reply above replaced the reset.

### Security headers

Source: [Security headers][t77]. [ADR 0014][adr14].

- **HSTS is on for every Route,** on HTTPS replies only: `Strict-Transport-Security: max-age=31536000`, with no `includeSubDomains` and no `preload`. It goes on the Edge's own 502 and 503 as well as on the Service's replies. The Service's own `Strict-Transport-Security` wins. The port-80 redirect and the 404 for an unknown Hostname send none.
- **No per-Route options before 1.0:** no `--no-hsts` and no extra response headers, because either would need a new Route field and restart the 1.0.0 clock.
- **`Via` is removed** from replies sent to Visitors (RFC 9110 allows it). The `Via` Caddy adds to the request sent to the Service stays.
- **The Edge's own replies send no `Server` header,** and the Service's `Server` passes through untouched. No reply to a Visitor names Caddy in `Via`, `Server` or any other header, or in the redirect's `Location`.
- **The Edge's own replies are hardened:** the error pages, the event-stream `200` and the port-80 redirect carry `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'` (the page has inline CSS, no JS and no external requests). Replies from a Service get none of these; CSP, framing, referrer and `Permissions-Policy` are the Service's to set.
- **Not checked in the test run:** the SSL Labs grade of A+ needs an Edge deployed on a public Hostname, and is checked by hand once there is one.

### Liveness

Sources: [Reconnects][t14], [Version skew][t15].

- **The Outpost** keeps WireGuard's persistent keepalive at 25 s and pings every 10 s.
- **An Outpost is Offline** once nothing has arrived from it for 60 s. The Edge's own start counts as hearing from every Outpost. When an Outpost goes Offline, the Edge closes all its Tunnel connections, uploads included.
- **TCP keepalive on every Tunnel connection,** dialled or accepted, on both sides: 5 s idle, a 3 s interval and 3 probes. There is no TCP user timeout.
- **Lost closes do not hang a stream.** A Visitor's stream through an Outpost whose Tunnel connections are gone ends within 15 s (5 s idle + 3 probes 3 s apart), even if the Outpost's closes never arrived because its last packets were lost, and even though the Outpost is not Offline yet. An Outpost that has restarted answers the first probe with a reset, so older streams through it end in the same time, with the Outpost back or not. Picks, from the ways considered in #79:
  - **(d) tighter keepalive** is the bound. It needs no wire change.
  - **(c) closing on Offline** stays as the backstop for anything keepalive misses (60 s).
  - **(b) restart detection** is not built. Neither the ping nor WireGuard's handshake tells a restart from a rekey without a session tag in the ping, which would be a wire change; the reset above makes it unnecessary.
  - **(a) flushing closes before exit** is not built: the bound does not depend on it, and the Outpost still exits at once.
- **After an Edge restart,** the Edge pings every remembered endpoint at once. The Tunnel is back within one round trip if the Outpost's NAT still maps that endpoint. If not, the Outpost's next ping brings it back within about 25 s.
- **The Edge's address:** `wireguard-go` takes only IPs, so the Outpost resolves `--address` itself:
  - after 30 s of unanswered handshakes
  - then every 30 s while the Tunnel stays down

  It switches when the address has changed.
- **An Outpost never gives up,** and never exits on its own.
- **Reconnect bursts get nothing special:** no rate limit, queue or jitter.

### Stopping

Source: [Reconnects][t14].

- **The Edge, on SIGTERM:**
  1. stops accepting connections
  2. ends every event stream and WebSocket at once
  3. lets other in-flight requests finish for up to 10 s, moving on as soon as they're done
  4. actively closes every remaining connection, HTTP/3 included
  5. exits

  tnl does this in its router and transport, because an embedded `caddy.Stop()` waits for nothing.
- **An Outpost, on SIGTERM,** closes every connection and exits at once.

### Outposts

Sources: [Joining][t6], [Declaring the Edge's Zones and Outposts][t28].

These commands manage Outposts on an Edge that doesn't declare them. An Edge that does refuses them, and its Outposts follow [Declared Zones and Outposts](#declared-zones-and-outposts).

- **`tnl outpost add <name> [--ttl D]`** assigns the Tunnel address, creates the one-time key pair and installs its public half as a peer, with the token's expiry `--ttl` from now (1 h by default). It prints the join token and two `install.sh` lines pinned to the Edge's version, one per line: the first with `sudo` for Linux (the systemd install), the second without for macOS (the per-user install). The Edge doesn't know the Outpost's OS, so it prints both, and says on stderr which is which. A build with no release version (`dev`) prints the `releases/latest` line and says on stderr that it is not pinned. Names are unique, use DNS-label characters and never change.
- **`tnl outpost rm <name>`** refuses while Routes point at the Outpost, and lists them. `--with-routes` removes those Routes too.
  - Removal also removes the Outpost's Declaration, drops its peer and closes its connections.
  - Removing an Outpost that hasn't joined cancels its token.
  - An Outpost can't remove itself.
- **`tnl outpost rekey <name> [--ttl D]`** revokes the current key at once, and prints a new token and install line for the same name. Joining with it keeps the name, Tunnel address, Routes and Declaration. There is no automatic rotation.
- **The Edge's WireGuard key** never rotates in v1. Changing it means rekeying every Outpost.

### Routes

Sources: [Route management][t7], [Zones and certificate modes][t8].

- **A Route** is a Hostname, an Outpost, a Service URL, `--insecure-skip-verify` and `--host-header`, and nothing else: no path routing, custom headers or TLS server name ([ADR 0004][adr4]).
- **The Hostname** is exact, never a wildcard, inside some Zone, and held by at most one Route. Adding a taken Hostname is refused, naming the Outpost that holds it. An Outpost can never take a Hostname over.
- **The Service URL** is `http://` or `https://`, a host and an optional port, with no path. The port defaults to 80 or 443.
- **`route add`** saves the Route and swaps it in. Then, after the lock:
  - it obtains the certificate if no wildcard covers the Hostname, waiting up to about 60 s. It warns on failure, and Caddy keeps retrying.
  - it test-dials the Service through the normal data path, including the TLS handshake for a verified `https://` Service. The test dial is one attempt, without a request's retries, so `route add` never waits on a Service that is down; it is skipped when the Outpost is Offline or has not connected yet.
  - it resolves the Hostname

  It warns if the Outpost is Offline, the allowlist refuses the Service, the Service doesn't answer, the certificate fails (with a hint for `--insecure-skip-verify`), or the Hostname doesn't point at the Edge. In a wildcard Zone, a name the wildcard doesn't cover gets a note that it will appear in Certificate Transparency logs. The Route is saved either way.
- **`route edit`** closes the Route's open connections, even when only an option changed, and test-dials when the Service changed.
- **`route rm`** closes the Route's connections too. Other Routes are never touched.

### Zones and certificates

Sources: [Zones and certificate modes][t8], [Wildcard certificates through Hetzner and Cloudflare DNS][t4], [Observability][t16], [Declaring the Edge's Zones and Outposts][t28].

- **A Hostname belongs to the longest Zone that contains it.** A Zone's own name is in it, and Zones may nest. Hostnames outside every Zone are refused and never get a certificate.
- **A per-Hostname Zone** (`tnl zone add <zone>`) gives each Route Hostname its own certificate, obtained at `route add` and renewed in the background. On-demand issuance, gated by the permission module, stays as the fallback. These Zones never touch Caddy's config.
- **A wildcard Zone** (`tnl zone add <zone> --wildcard cloudflare`) gets one certificate for `*.<zone>` and `<zone>` through DNS-01:
  1. The token is read with a hidden prompt on a terminal and from stdin otherwise, never from an argument or a variable. A declared Zone takes it from its line instead ([Declared Zones and Outposts](#declared-zones-and-outposts)).
  2. The Edge finds the provider's DNS zone by SOA lookup and prints it.
  3. It refuses the Zone if the token can't read that DNS zone. This is the one hard gate.
  4. It obtains the wildcard, waiting up to about 60 s and warning on failure, and prints the names it covers.

  Deeper names, like `a.b.<zone>`, get their own certificate. The docs give the token's scopes: Zone·Zone·Read and Zone·DNS·Edit, limited to that DNS zone.
- **Tokens** live in `state.json` and are read when a challenge runs. They are redacted from every error, and deleted when a Zone leaves wildcard mode or is removed. `zone edit --token` replaces one after the same check, with no reload.
- **Adding, removing or switching a wildcard Zone reloads Caddy.** SSE streams survive, and every WebSocket on every Route closes ([ADR 0005][adr5]).
- **Switching mode never shows a Visitor a certificate error.**
  - The new certificates are obtained first, and the old ones serve until replaced. Caddy's reload would drop a certificate it no longer manages from its cache, so the Edge also names in the new config's `automate` list every wildcard certificate in storage whose Zone is no longer a wildcard and that hasn't expired, each name by its own certificate's expiry. They fall under the catch-all policy, which is on-demand, so Caddy loads them from storage, keeps them in its cache and, as certmagic's maintenance skips on-demand certificates, renews none. They are dropped at the first reload after they expire.
  - Per-Hostname certificates stay managed until the wildcard is in, which means its certificate is in storage or Caddy's cache and unexpired; then they stop renewing. A certificate the apex has of its own doesn't count as the wildcard.
  - A dropped wildcard keeps serving Hostnames that don't have their own certificate yet, until it expires. The reply waits up to about 60 s for each Route's own certificate and warns if one isn't there.
  - When Caddy manages a wildcard, it takes it to cover every name below it and gets no certificate for them. The config therefore names the Route Hostnames the certificate manager holds as well, each under a policy of its own that isn't on-demand, and automates them. That is certificate management only: the config still holds no Routes, and a Route change never reloads Caddy.
  - Adding a nested Zone moves the Routes it contains under the same rule.
  - **A restart doesn't either.** Caddy fills its certificate cache from storage in the background, so a handshake that landed just after the listener opened found no certificate and got a TLS internal error. When the Edge starts, it first loads the TLS app alone, with no listener, waits (up to 10 s) until every unexpired certificate in storage for a name the config automates is in the cache, and only then loads the full config, which keeps the cache. An Edge with nothing in storage skips the first load.
- **`zone rm`** is refused only if it would leave Routes outside every Zone, and the refusal lists them.
  - `--with-routes` removes those Routes, and a declared one goes back to waiting.
  - Routes that a parent Zone still contains move to it.
  - Removal deletes the token and stops renewing the Zone's certificates.
- **DNS checks only warn:** `zone add` resolves a random name under a wildcard Zone, and `route add` resolves the Hostname.
  - A per-hostname Zone gets no random-name check: it needs only each Hostname to point at the Edge, which `route add` checks, and a wildcard record elsewhere is a valid setup for it.
  - A declared Zone gets the check only when its line is new or its mode changed, never at a restart with the line unchanged.
- **There is one CA:** Let's Encrypt by default, or whatever `--acme-ca` names. There is no per-Zone CA and no `_acme-challenge` delegation by CNAME.

### Declarations

Sources: [Routes declared on the Outpost][t17], [ADR 0009][adr9].

- **Syntax:** `TNL_ROUTE_<LABEL>=<hostname> <service-url> [--host-header V] [--insecure-skip-verify]`, or the same arguments in a repeated `--route`.
  - `<LABEL>` is letters, digits and `_`. It names the line in messages and never reaches the Edge.
  - Values are split on whitespace, with no quoting.
- **Lines are checked at start.** The Outpost refuses to start, with exit code 78, on:
  - a syntax error or an unknown option
  - a Service URL with a path, or a scheme other than `http` or `https`
  - an invalid Hostname
  - the same Hostname on two lines
  - `--route` mixed with `TNL_ROUTE_*`

  The error names the variable: `TNL_ROUTE_MEDIA: unknown option --host-heder`. A `--route` line is named by its text: `--route <line>: …`.
  - Hostnames are lower-cased and the Service URL is canonical, so both forms of a line parse to the same Declaration. An option may appear once, `--host-header` takes the next word, and `--host-header=V` is an unknown option. An empty variable, a missing label (`TNL_ROUTE_`) and a label outside letters, digits and `_` are errors.
  - The "did you mean" suggests the known variable within an edit distance of 3, and says only "unknown variable" when none is that near. The `TNL_ROUTE_` prefix is known on `tnl connect` only; `tnl edge` refuses it with "`TNL_ROUTE_PHOTOS`: Routes are declared on the Outpost; set `TNL_ROUTE_*` there", exit code 78.
- **The Declaration is sent when the digests differ.** When the ping's answer says the Edge's copy differs, the Outpost sends its whole Declaration, even an empty one. If the Edge refuses it whole (an unknown field, an Incompatible Outpost or any other refusal of the Declaration itself, a 4xx status), nothing changes, the Outpost logs a `warn` once, and it sends it again only when the Edge's version changes. A send that gets no answer, or a server error (5xx), is tried again at the next ping. The Outpost sends the lines in the form it parsed them, and the Edge refuses a line that isn't in that canonical form.
- **It is applied as a diff by Hostname, in one locked change.**
  - An unchanged line keeps its Route and its connections.
  - A changed line counts as an `edit`.
  - A line that's gone counts as an `rm`.
- **Lines that can't apply yet wait.** A line whose Hostname another Outpost holds, or that is outside every Zone, waits in the Declaration, while every other line applies.
  - A waiting line becomes a Route by itself, in the same locked change that frees its Hostname or adds a Zone for it.
  - If several Outposts wait for one Hostname, the one that declared it first gets it.
  - The command that freed the Hostname says so: "newbox declared photos.example.com and now serves it".
  - The handover is part of the state store's change path, not a step in each handler. After a change's function has run, and before the result is checked and saved, the store gives every free Hostname inside a Zone to the line waiting for it, oldest first, and ties go to the Outpost whose name sorts first. Every command therefore gets it, and no other change can see the Hostname free.
  - `route edit` moving a Route frees nothing: the Hostname stays held, now through the other Outpost. The handover runs after it like any change and finds nothing to do. A Route of a declaring Outpost can't be moved at all.
  - A Declaration that drops a line, `outpost rm`, `route rm` and `zone add` free a Hostname or add a Zone. `zone rm --with-routes` removes the Routes in the Zone and leaves the lines, so a declared Route is waiting again with the reason `outside every Zone`.
  - The waiting lines are logged by the Edge as `declared line waits` at `warn`, `declared line still waits` at `warn` on the shared reminder schedule (5 min, 30 min, then hourly), and `declared line applies` at `info` in the change that applied it, with the Outpost and Hostname as fields.
- **After the lock,** the Edge test-dials new lines and lines whose Service changed, in parallel, and replies with the outcome. New Hostnames get their certificates in the background, and nothing waits for them. The exception is a Route made by a handover: it is created inside another command's change, which replies about its own lines only, so the Route is not test-dialed.
- **There is one source per Outpost.** While an Outpost's Declaration isn't empty, it is the whole truth:
  - `route add`, `edit` and `rm` are refused for its Routes, from both sides: "nas declares its Routes; change `TNL_ROUTE_*` on nas and restart it", with status 409.
  - Switching from the CLI replaces the Routes the CLI made, and each removal is logged at `warn` on both sides.
  - An empty Declaration from an Outpost that declares removes all its Routes and hands it back to the CLI.
  - An empty Declaration from an Outpost on the CLI changes nothing.
- **The Edge host keeps** `outpost rm`, which removes the Declaration too, and `zone rm --with-routes`. `rekey` keeps the Declaration.

### Declared Zones and Outposts

Sources: [Declaring the Edge's Zones and Outposts][t28], [ADR 0010][adr10], [ADR 0011][adr11].

- **Syntax:**
  - `TNL_ZONE_<LABEL>=<zone> [--wildcard PROVIDER (--token-file PATH | --token VALUE)]`, or the same arguments in a repeated `--zone`.
  - `TNL_OUTPOST_<LABEL>=<name> <public-key>`, or the same in a repeated `--outpost`. The key is standard base64, as in `wg`.
  - Labels and splitting follow [Declarations](#declarations): `<LABEL>` is letters, digits and `_`, and values are split on whitespace, with no quoting.
  - `--token` exists only in `TNL_ZONE_*` variables, where the token sits in a variable anyway. A `--zone` flag takes `--token-file`, and `tnl zone add` keeps its prompt.
  - These are declared Zones and declared Outposts. "Declaration" stays the name of an Outpost's Routes.
- **Lines are checked at start.** The Edge refuses to start, with exit code 78, on:
  - a syntax error or an unknown option
  - an invalid Zone, name or key
  - the same Zone or name on two lines, or the same key on two Outposts
  - a wildcard line without exactly one of `--token-file` and `--token`, an unknown provider, or a token file that's missing, unreadable or empty
  - two names whose derived Tunnel addresses collide, naming both
  - a key in `--key-file` or `TNL_KEY` that doesn't match `state.json`'s
  - both forms of one setting: `--zone` with `TNL_ZONE_*`, `--outpost` with `TNL_OUTPOST_*`, `--key-file` or `TNL_KEY_FILE` with `TNL_KEY`
  - `TNL_ROUTE_*`, which belongs on the Outpost

  The error names the variable: `TNL_ZONE_MAIN: unknown option --wildcrd`. A `--zone` or `--outpost` line is named by its first word: `--zone example.com: …`. **No message carries a value:** a bad key, token or credential is reported as bad, never shown, and the "did you mean" lists names only. The key mismatch names where the key came from: `--key-file`, `TNL_KEY_FILE` or `TNL_KEY`. A token reaching the Edge's logs or errors by any other road is replaced with `[redacted]`.
- **They are applied at start as a diff by name, in one locked change,** before Caddy's config is built. Each item is saved in `state.json` and marked as declared.
  - An unchanged line changes nothing.
  - A new Zone line counts as `zone add`. A changed mode or token counts as `zone edit`, with its switch that never shows a certificate error.
  - A new Outpost line adds the Outpost at its derived address, already joined, with no token. A changed key counts as `rekey`: the old key is revoked at once, and the Outpost keeps its name, Routes and Declaration. Declaring a name that exists as a CLI Outpost adopts it the same way, and moves it to its derived address.
  - A Zone line that's gone counts as `zone rm --with-routes`: Routes from a Declaration go back to waiting, and Routes that a parent Zone still contains move to it. If a Route made with the CLI would end up outside every Zone, the Edge exits 78 instead, naming the Zone and the Routes: "example.com is no longer declared, but app.example.com, git.example.com are in it; remove them or declare the Zone again".
  - An Outpost line that's gone counts as `outpost rm --with-routes`.
  - Each removal is logged at `warn`, each other change at `info`.
  - A Zone line for a CLI Zone's name adopts it: the Zone keeps its Routes and takes the line's mode and token.
- **Remote checks never stop the Edge.** After the lock, a new or changed wildcard token gets the `zone add` token check. If it fails, the Edge logs an `error`, keeps the Zone, and retries the wildcard like any failed issuance. The check is repeated on the shared reminder schedule (5 min, 30 min, then hourly), with an `error` each time it fails and an `info` when it passes. The other `zone add` checks warn as they do there.
- **There is one source per kind.** While any `TNL_ZONE_*` is set, the declared Zones are the Edge's Zones:
  - `zone add`, `edit` and `rm` are refused: "Zones are declared; change TNL_ZONE_* and restart the Edge".
  - The first start with declared Zones removes the CLI's Zones that aren't declared, under the rule above.

  `TNL_OUTPOST_*` works the same way, with `outpost add`, `rekey` and `rm` refused, and the CLI's Outposts that aren't declared removed as `outpost rm --with-routes`. An Edge that declares its Outposts mints no join tokens.
- **No lines of a kind hands it back to the CLI.** If `state.json` holds declared Zones and no `TNL_ZONE_*` is set, the Zones stay, lose their mark, and a `warn` says so. Outposts work the same way. So removing the last line doesn't remove its item: follow with `zone rm` or `outpost rm`.
- **Declared Outposts don't join.** Each connects with its [Outpost credential](#outpost-credential) from the first packet, and is never `not joined`. One credential runs one Outpost: two copies fight over the peer's endpoint, and v1 doesn't detect it.
- **Routes aren't declared on the Edge.** They stay declared on Outposts, so each Outpost keeps one source for its Routes. An Outpost on a declaring Edge still uses `tnl route` or its Declaration.
- **Minting, offline:**
  - `tnl keygen` prints a new private key in `wg genkey` format, for `--key-file`. `wg genkey` works too.
  - `tnl credential <name> --address A [--wireguard-port N] [--key-file F]` reads the Edge's private key from `--key-file` or `TNL_KEY`, makes the Outpost's key pair, and prints the Edge's line and the credential:

    ```
    TNL_OUTPOST_NAS=nas 6WvT…=
    TNL_CREDENTIAL=tnlc1.…
    ```

    The label is the name in upper case, with `-` as `_`. It never contacts an Edge, and runs wherever the full build does, `docker run --rm` included.
- **Rotating a credential:** mint a new one for the same name, change both lines and restart both sides.
- **Changing the Edge's `--address` or WireGuard port** means minting every credential again, which is one more reason to give `--address` a DNS name.

### Backup and restore

Source: [Where the Edge keeps its state][t11].

- **`tnl backup <file>`** (`-` for stdout) runs on the Edge host. It asks the running Edge for one tar archive, created 0600, holding:
  - `state.json`, copied under the lock
  - `caddy/`, without its lock and temp files

  Certificates whose key doesn't match are left out and named. Caddy obtains them again after a restore.
- **No encryption, schedule or history.** Operators pipe the archive into `age`, restic or cron. Startup settings aren't in it, so neither is `--key-file`: keep it beside the backup.
- **To restore:** stop the Edge, replace the state directory's contents with the archive's, and start it. Before 1.0 there is no migration: a backup whose `state.json` has a different schema version is refused at start. From 1.0, an older backup is migrated on start.
  - Outposts that joined before the backup reconnect without rekeying, even on a new VPS, as long as `--address` moves with it.
  - Outposts added or rekeyed after the backup need `outpost add` or `rekey` again. Declared Zones and Outposts are brought up to date from the Edge's settings at start.
  - Route and Zone changes made after the backup are lost.
  - Waiting lines come back, and each Outpost resends its Declaration if it differs from the restored copy.
- **Restoring without `caddy/` works, at a cost.** Every certificate is obtained again, against Let's Encrypt's rate limits, and a lost account key means registering a new account.

- **`--outpost`** is required for `route add` on the Edge host and is accepted by `route edit` there. It doesn't exist on an Outpost, where the Edge fills in the caller.
- **`--host-header ""`** clears the override.
- **Every command takes `--state-dir`** to pick the process to talk to.
- **`tnl version`** prints the version, the build (`full` or `outpost`) and one compatibility line, such as "works with Edges and Outposts 1.x", or "accepts Outposts 1.x and 2.x" on a 2.x full build. Before 1.0 the line names the minor, "works with Edges and Outposts 0.3.x", because that is the window. A `dev` build says it works with any version.
- **Help** comes from one table in the source, which a test checks against the commands, their flags and this table:
  - `tnl help [command...]`, `-h` and `--help` work at every level, print to stdout and exit 0. A command's help gives its usage, each argument and flag with its default and variable, where it runs and examples.
  - Flags show as `--flag`; the single-dash form keeps working.
  - An unknown command or a missing argument prints a short usage line and a pointer to `tnl help ...` on stderr, with the exit codes below.

Where a process is found, it also completes Outpost names, Route Hostnames and Zones through the local socket, waiting up to 2 s and printing nothing on failure. `install.sh` does not install it; the [guide](../guide/completion.md) says how.
- **In the Outpost build,** `edge`, `outpost`, `keygen`, `credential`, `backup` and `zone add`, `edit` and `rm` say "this is the Outpost build" and point to the full one.
- **On an Outpost whose Tunnel is down,** commands that reach the Edge fail with "Outpost not connected".
- **Exit codes:**
  - `0`: done, warnings included
  - `1`: refused or failed
  - `78`: a config error in `tnl edge` or `tnl connect`

- **`outpost ls`,** sorted by name: NAME, STATE, LAST SEEN, ENDPOINT, VERSION, TUNNEL ADDRESS, ROUTES. Declared Outposts are marked.
- **`route ls`:** HOSTNAME, OUTPOST, SERVICE, OPTIONS, STATUS. Waiting lines get rows of their own. An older Outpost prints fields it doesn't know as `name=value` in a last column.
- **`zone ls`:** ZONE, MODE, PROVIDER, CERTIFICATE. It never shows a token. Declared Zones are marked.

## 8. Logs and status

Sources: [Observability][t16], with amendments from [Routes declared on the Outpost][t17].

### Logs

- **stderr only.** There is no log file, rotation or `--log-file`. When `JOURNAL_STREAM` shows that stderr is the journal, tnl leaves out its own timestamp and prefixes each line with its syslog priority, so `journalctl -p warning` works.
- **`tnl logs` reads a ring, not a file.** The process keeps its own log lines in memory, at the level it is configured to write to stderr, and serves them over the local socket, so `tnl logs` works the same under systemd, Compose and a bare `tnl connect`. It holds the last 1000 lines or 1 MiB, whichever is smaller, and drops the oldest. **The access log stays out of it:** `request` lines written for `--access-log` go to stderr only, since their volume would push out the lines an operator is looking for; the request lines for responses the Edge made itself are tnl's own lines and are in it.
  - `tnl logs [-f] [-n N] [--since D] [--level L] [--json]` prints the lines held in the format the process logs in, each with its timestamp, even when stderr is the journal. `--json` prints JSON lines whatever the format. `-f` follows until interrupted, which ends with exit 0. `--level` shows that level and above, `--since` lines newer than the duration, `-n` the last N after the other filters.
  - It finds the process like every client command (`--state-dir`, `TNL_STATE_DIR`, discovery) and exits 2 when none is found, as `tnl status` does.
  - On an Outpost the relay answers it from the Outpost's own ring; the call never reaches the Edge, and an Outpost can't read the Edge's.
  - A follower that can't keep up loses lines; logging never waits for it.
  - The ring and the reply are `local` only, so **they are not an API either:** `tnl logs --json` is the process's log format, which this spec doesn't fix.
- **`key=value` text by default,** or JSON with the same fields through `--log-format json`. Messages are short fixed strings, and everything variable is a field. **Logs are not an API:** `--json` on the CLI is the stable surface (`tnl logs --json` is only the log format as JSON).
- **Four levels, `info` by default:**
  - `error`: broken now, and it won't recover without the operator
  - `warn`: a Visitor will notice, or the operator should look
  - `info`: changes of state
  - `debug`: every attempt
- **Transitions and spaced reminders, never every attempt.** Anything that can stay wrong for hours logs when it starts, reminds after 5 min, 30 min and then hourly, and logs when it ends. Certificate failures remind daily.

**The Edge logs:**
- **At start:** version, build, `--address`, WireGuard port, key fingerprint, and the number of Outposts, Routes and Zones, with how many are declared. A refusal at start is `error`, followed by the exit.
- **Declared Zones and Outposts:** `info` for each change the diff applies, `warn` for each removal and hand-back to the CLI, and `error` for a wildcard token that fails its check, with reminders.
- **Every state change, at `info`,** with `actor=outpost:<name>` or `actor=local`. A refusal on save is `warn`.
- **Every warning the CLI printed, at `warn`,** so the Edge's log tells the whole story even when an Outpost made the change.
- **Outpost transitions:**
  - Offline: `warn`
  - back online: `info`, with how long it was gone
  - Incompatible: `warn`, with both versions, once per version change
  - a new public endpoint: `info`
- **Declarations:** `warn` when a line starts waiting, with reminders, and `info` when it applies.
- **At stop:** how many requests drained (`drained`) and how many streams were cut (`streams_cut`), and how many requests were still running after the drain and were closed (`closed`).

**An Outpost logs:**
- **At start, at `info`:** name (from the join exchange, or from the credential), version, Tunnel address, the Edge's address, the state directory and the allowlist.
- **"Tunnel up", at `info`:** the Edge's address, resolved IP and version, with how long the outage lasted.
- **"No answer from the Edge", at `warn`,** after 30 s of silence. It names the address and IP it tried and both possibilities: "the Edge is down or unreachable, or this Outpost was removed or rekeyed on the Edge". It reminds on the schedule above. A routine Edge restart raises no warning.
- **At `info`:** a changed Edge address, Route changes made through its CLI, and each allowlist refusal, with the request ID and the address the Edge named.
- **After each Declaration send:**
  - a summary at `info`: the message `Declaration sent` with the counts as fields, for example `declared=5 added=1 changed=1 removed=0 waiting=1`
  - `info` for each change
  - `warn` for each waiting line, naming its variable (`variable=TNL_ROUTE_MEDIA`, or the `--route` text)
  - `warn` for each failed test dial, and for each Route made with the CLI that the Declaration replaced

  When the Edge's digest of its Routes changes, it logs a line that now applies (`info`, `Route now applies`) or has started waiting (`warn`, `Route started waiting`). After a start with a matching digest it logs a `warn`, `Route waiting`, for each line that still waits.
- **At `debug`:** retries, re-resolutions, connections and dial failures.

**Request lines:**
- **Every response the Edge makes itself gets one `info` line:** a 502 or 503 (an event-stream request included), a request cut because the Outpost's connection dropped, and a 404 for a Hostname inside a Zone. A 404 for a Hostname outside every Zone is `debug`.
- **Successful requests, and whatever the Service answered,** are logged only with `--access-log`.
- **One line per request, written when it ends,** with these fields:
  - `id`, `visitor` (IP:port), `host`, `method`, `path` (without the query string) and `proto`
  - `status`, plus `event_stream=true` for an event-stream request answered with `200` and `retry:`. `status` is then the 502 or 503 the Edge would have sent, not the `200` the Visitor got
  - `duration`, `bytes_in`, `bytes_out` and `outpost`
  - `reason` for failures: `refused`, `timeout`, `dns`, `allowlist`, `outpost offline` (the Outpost is Offline, or its connection dropped under the request), `tunnel not up` (the Outpost was not Offline, but its Tunnel did not come back within the 10 s wait), `outpost incompatible` or `no route`
- **Never logged:** the query string, headers, cookies, User-Agent or Referer.
- **The request ID rides in the tnl header,** so the Outpost's lines about that connection carry it. It is the ID of the request that opened the Tunnel connection; a later request sent over the same kept-alive connection has an ID of its own that the Outpost's lines do not carry.

**Certificates:**
- obtained or renewed: `info`, with the name, issuer and expiry, plus "after N failed attempts" when there were some
- the first failed attempt: `warn`, with the error and the time left until expiry
- further attempts: `debug`, with a daily `warn` reminder
- once the certificate has expired, the daily line becomes `error`

The lines are `certificate obtained` and `certificate renewed` (`hostname`, `issuer`, `expires`, `after_failed_attempts` and `failing_for` when there were failures), `certificate attempt failed` (`hostname`, `error`, `failed_attempts`, and `time_left` for a renewal) and `certificate still failing` (the daily reminder, with `time_left` or `expired_for`). One reminder schedule, `internal/remind`, drives every "transitions and spaced reminders" line, so the Outpost's lines reuse it.

### Caddy and wireguard-go

- **Caddy's entries become tnl lines** through the log core, keeping Caddy's logger name (`logger=tls.obtain`). Levels are remapped:
  - `tls.*` obtain and renew chatter, and the per-handshake "in renewal window" line: `debug`
  - `http.log.error`, `http.handlers.reverse_proxy` and `http.stdlib` handshake errors: `debug`
  - everything else keeps its level
- **tnl always supplies `logs.default` and no `sink`,** so Go's `log` package follows `slog.SetDefault`.
- **`wireguard-go`'s `Verbosef` and `Errorf` both go to `debug`.** Use `DiscardLogf` when debug is off, because a nil log function panics.
- **Known exceptions,** listed in the docs:
  - one "redirected default logger" line from Caddy at each start
  - one JSON line from Caddy, `unable to determine directory for user configuration`, written while the package initialises, before `main`, when a binary is run by hand with neither `XDG_CONFIG_HOME` nor `HOME` set. `tnl-edge.service` sets `XDG_CONFIG_HOME=/var/lib/tnl/config` so the unit never prints it. The Outpost build links no Caddy and is unaffected
  - certmagic's stale-lock messages, which go to raw stderr and appear only after a crash

### Status

- **An Outpost's state** uses the same words on every surface:
  - `online`: heard from in the last 60 s, with a version inside the window
  - `offline`: nothing heard for 60 s
  - `incompatible`: heard from, but its version is outside the window
  - `not joined`: added, with its token unused. A declared Outpost is never `not joined`.
  - `never connected`: joined or declared, and the Edge has no record of it ever connecting, and has not heard from it since it started. It is not counted online. After the usual 60 s from the Edge's start it is `offline`.

  For up to 60 s after an Edge restart, an Outpost that has connected before and is not yet heard from shows `online`, with LAST SEEN "–". What tells the two apart is the Outpost's saved endpoint, which the Edge writes at its first handshake, so `state.json`'s shape does not change.
- **`outpost ls` columns:**
  - **LAST SEEN** is relative ("4s ago"). A `not joined` row shows "token expires in 42m" or "expired" there instead.
  - **ENDPOINT** is the public IP:port last heard from.
  - **VERSION** is "–" when unknown.
  - **ROUTES** is a count, or "3 declared" for an Outpost that declares.
- **`route ls` STATUS** shows the first problem in this order:
  1. `outpost not joined`, `outpost never connected`, `outpost offline` or `outpost incompatible`
  2. `no certificate` or `certificate expired`
  3. `renewal failing`
  4. otherwise `ok`

  A waiting row shows `waiting: taken by nas` or `waiting: outside every Zone`. During a move, a Hostname shows two rows.
- **`zone ls` CERTIFICATE:**
  - for a wildcard Zone: `valid until 2026-12-01`, `obtaining`, `renewal failing for 3d: <error>`, `failed: <error>` or `expired`
  - for a per-Hostname Zone: a summary, such as `12 certificates, 1 failing`
- **On an Outpost,** `route ls` and `zone ls` show the same as on the Edge.
- **`tnl status` on the Edge** prints:
  - **a summary:** version and build, uptime, `--address` and WireGuard port, the key's fingerprint, the state directory, the log level and whether the access log is on, Outposts by state, the number of Routes and Zones, and the number of certificates with the soonest expiry
  - **Needs attention,** one line per problem:
    - each Offline or Incompatible Outpost, with when it was last seen and its number of Routes
    - each certificate failing renewal or expiring within 7 days
    - each waiting line, such as "newbox declares photos.example.com, which nas holds"

    Otherwise it prints "Nothing needs attention".
- **`tnl status` on an Outpost** prints:
  - its name, version, Tunnel address, state directory and allowlist
  - the Edge: `--address` and its resolved IP, the Tunnel's state ("up" or "no answer for 4m"), when the Edge last answered, and the Edge's version with any incompatibility message
  - its own Routes, fetched from the Edge, or "unavailable while the Tunnel is down"
  - its declared lines with their variables, and waiting lines with their reasons
- **`tnl status` exit codes:**
  - `0`: running, and nothing needs attention
  - `1`: running, but something needs attention. On an Outpost, that is a Tunnel that's down, an Edge that says it's Incompatible, or a line that's waiting.
  - `2`: no running Edge or Outpost was found, or its socket can't be opened
- **`--json`** on `status` and every `ls`:
  - RFC 3339 times, durations in seconds, and each certificate's expiry, state and full error
  - a `waiting` reason on waiting lines
  - `"declared": true` on declared Zones and Outposts
  - stable within a major, and changed only by adding

  Tables keep relative times, cut errors to one line, and may change in any release.

- **What the `ls` commands settle** (the table words and the `--json` fields; `--json` prints the Edge's reply indented, as it came, so what follows is the whole of its shape):
  - **Dash and marks.** An empty cell is "–" (an en dash). A declared Outpost or Zone has " (declared)" after its name.
  - **Not yet heard.** Right after a restart an Outpost the Edge counts as heard from, without a packet, because its saved endpoint shows it connected before, shows `online` and "–" for LAST SEEN, ENDPOINT and VERSION; the JSON leaves `last_seen` and `last_seen_ago_seconds` out. One with no saved endpoint, such as a declared Outpost that has not connected yet, shows `never connected` with the same "–" cells and the same omitted fields, and is not counted online; the 60 s window opens at the Edge's start, and then it shows `offline`. The state `never connected` is an addition to the frozen shapes, and so is `never_connected` in the status counts. A joined Outpost the Edge does not track at all (a declared Outpost added while it runs, before its first packet) shows `offline`, also with "–". Both go to `online` or `offline` by the 60 s rule as above.
  - **`outpost ls` JSON:** `name`, `state`, `last_seen`, `last_seen_ago_seconds`, `token_expires`, `token_expires_in_seconds` (negative once expired; the cell then says `expired`), `endpoint`, `version`, `tunnel_address`, `routes` (a count of Routes), `declared_lines` (the lines of its Declaration, waiting ones included, left out for an Outpost that declares none; the cell "3 declared" shows it instead of `routes`) and `declared`. `outpost ls` is refused to an Outpost with 403.
  - **`route ls` JSON:** `hostname`, `outpost`, `service`, `options`, `status` and, on a line that waits, `waiting`. `status` is the table's text: `ok`, `outpost not joined`, `outpost never connected`, `outpost offline`, `outpost incompatible`, `no certificate`, `certificate expired`, `renewal failing`, or `waiting: <reason>`. A waiting row shows its own reason and no Outpost problem.
  - **Waiting reasons** (the Outpost words them from the `wait_kind` of `GET /v1/declaration`, not from the Edge's log text) read `taken by nas`, `outside every Zone` or, for a free line the Edge has not applied yet, `not applied yet`. (The Edge's log keeps "held by Outpost nas".) A Route that moves shows its Hostname twice, the Route first and then the line that waits.
  - **Certificates in STATUS.** A Route is judged by its Hostname's own certificate, unless a held wildcard certificate covers it, which then counts as `ok`. `no certificate` is none held yet, whether it is still being obtained or failing. An expired certificate comes before one whose renewal is failing. An Edge with no web side knows nothing and says `ok`.
  - **`zone ls` JSON:** `name`, `mode`, `provider`, `declared`, and `certificate` for a wildcard Zone (the `*.zone` certificate) or `certificates` for a per-Hostname Zone, one for each Route Hostname the Zone holds that no held wildcard covers, sorted by name. Each is `name`, `state` (`valid`, `obtaining`, `renewal failing`, `failed` for failing with none ever held, or `expired`), `expires`, `failing_for_seconds` and `error` (in full). The cell reads `valid until 2026-12-01` (UTC), `obtaining`, `renewal failing for 3d: <first line of the error>`, `failed: <error>` or `expired`; for a per-Hostname Zone `12 certificates, 1 failing` (or `1 certificate`; the failing part only when something fails, counting `failed` and `expired` too). Without a certificate manager a wildcard Zone reads `obtaining`.
  - **Spans** in a table take their largest whole unit, "3d", "5h", "42m", "4s", and an error is cut at its first line and 100 characters.
  - **Fields a build does not know.** JSON only grows within a major, so the CLI reads every `ls` and status reply leniently and ignores a field it does not know, whichever object it sits in; the tables still print. An Outpost reads `GET /v1/declaration` the same way, so a field a newer Edge adds there costs `tnl status` nothing. Every other reply stays strict ([ADR 0012][adr12]). A Route's extra fields come out in a last column headed MORE as `name=value`. `--json` prints the reply's own bytes, indented, so every field reaches the script, known or not.
- **What `tnl status` on the Edge settles** (`GET /v1/status`; `--json` prints the Edge's reply indented, as it came):
  - **JSON:** `role` (`edge`), `version`, `build`, `revision`, `started`, `uptime_seconds`, `address`, `wireguard_port`, `key_fingerprint`, `state_dir`, `log_level`, `access_log`, `outposts` (`online`, `offline`, `incompatible`, `not_joined`, and `never_connected`, left out when zero, as counts), `routes` (Routes, not waiting lines), `zones`, `certificates` (`count` and `soonest_expiry`, left out when none is held) and `attention`, a list that is `[]` when nothing needs attention. Each item is `kind` (`outpost offline`, `outpost incompatible`, `certificate failing`, `certificate expiring` or `line waiting`), `subject` (the Outpost, the certificate's name or the Hostname), `message` (the table's line, free text) and, on a waiting line, `outpost`. An Outpost's status sits beside this reply under the same path, told apart by `role`.
  - **Certificates** are the ones `zone ls` shows: a wildcard Zone's, and one for each Route Hostname no held wildcard covers. The count is those that hold a certificate, and the soonest expiry is among them. One that fails (`renewal failing`, `failed` or `expired`) is a `certificate failing` item, and one that is valid but expires in under 7 days (168 h) is `certificate expiring`; never both.
  - **Outposts.** An Offline or Incompatible Outpost is a problem; `not joined` is not, and neither is `never connected` within its window, which `Outposts:` counts apart from `online`. A joined Outpost the Edge has not heard from since it started, and has run past the 60 s window, is Offline with "not heard from since the Edge started" in place of when it was last seen.
  - **Waiting lines.** Every waiting line counts, including `not applied yet`: "newbox declares photos.example.com, which nas holds", "..., which is outside every Zone" or "..., which is not applied yet". The items are ordered Outposts, then certificates, then waiting lines.
  - **Exit codes.** `2` is also what a failed discovery gives when several processes are running and none is pinned, and when a pinned `--state-dir` has no socket that opens. A CLI and process of different versions, and any other error, exit `1` with the message on stderr, as the other commands do. Needs attention is printed to stdout, and `1` for it prints nothing more.
- **What `tnl status` on an Outpost settles** (the Outpost's relay answers `GET /v1/status` itself, `local` only; `--json` prints its reply indented, as it came):
  - **JSON:** `role` (`outpost`), `name`, `version`, `build`, `revision`, `tunnel_address`, `state_dir`, `allow` (as given; left out when the Outpost has no allowlist, which text shows as "no limit"), `edge`, `routes`, `routes_unavailable`, `declared` (left out when the Outpost declares nothing) and `attention`, `[]` when nothing needs attention. `edge` is `address` (`--address` as given), `ip`, `state` (`up` or `down`), `last_answer` (left out before the first answer), `silent_seconds`, `version`, `incompatible` (the Edge says this Outpost is outside its window), `too_old` (the Edge is of an older major than the Outpost works with; left out otherwise) and `message` (the words for either). `routes` is each applied Route as `hostname` and `service`, and is `null` while the Tunnel is down, with `routes_unavailable` giving the words ("unavailable while the Tunnel is down"). `declared` is each declared line as `hostname`, `service`, `variable` (`TNL_ROUTE_MEDIA`) and, on a waiting line, `waiting` and `reason`. Attention items are those of the Edge's, with the kinds `tunnel down`, `edge incompatible`, `edge too old` and `declared line waiting` (subject: the Edge's address, or the Hostname).
  - **The Tunnel is down** once the Edge has been silent for the "No answer from the Edge" time (30 s); a shorter silence, such as an Edge restart, is `up`. Before the first answer, `last_answer` is left out and the text says "not yet".
  - **Routes** are fetched from the Edge when the Tunnel is up, with the same 5 s bound as any relayed call. If the Edge refuses the call (an Incompatible Outpost), `routes_unavailable` carries its message; if the call fails or its reply can't be read, it says "could not be read from the Edge: " and the cause, which is not the Tunnel being down. The waiting lines come from the same call and are not in `routes`, and while the Tunnel is down no line is shown as waiting.
  - **Waiting reasons** use the `ls` words (`taken by nas`, `outside every Zone`, `not applied yet`), not the Edge's log wording.
  - **Exit 1 also covers an Edge too old for this Outpost** (an older major, which the Outpost keeps trying with): it can't work with it, so it needs attention like an Incompatible one. It is its own fact, `too_old` and the attention kind `edge too old`, and never sets `incompatible`, which is only what an Edge says of the Outpost. The Edge's version in the text carries the message.
- **Not in v1:** a metrics endpoint, notifications, or a Docker `HEALTHCHECK`.

### install.sh

- **The Edge:** `curl -fsSL https://github.com/hyprsh/tnl/releases/latest/download/install.sh | sudo sh -s -- edge --address edge.example.com`
- **An Outpost:** `… | sudo sh -s -- outpost --token <t>` on Linux, and `… | sh -s -- outpost --token <t>` on macOS, where the install is per-user and `sudo` would make it root's.
- **Without systemd or root:** the script installs only the binary, to `~/.local/bin`, and prints `tnl connect --token …`.

**What it does:**
1. Checks the binary against the release's `SHA256SUMS`.
2. Installs it to `/usr/local/bin/tnl`.
3. Installs the unit from the release archive.
4. Writes `/etc/tnl/edge.env` (`TNL_ADDRESS`) or `/etc/tnl/outpost.env` (`TNL_TOKEN`), but never overwrites an existing one.
5. On Linux as root, writes `/etc/sysctl.d/60-tnl.conf` and applies it with `sysctl -p` (see the rules).
6. Starts the unit.

**Rules:**
- **Each release attaches its own `install.sh`,** which installs that release's version. `releases/latest/download/…` gets the latest, and `releases/download/vX.Y.Z/…` pins one.
- **Re-running it is the upgrade:** it swaps the binary atomically and restarts whichever tnl units are active.
- **It never replaces a full build with the Outpost build** on a host that runs both roles.
- **Socket buffers:** quic-go (the Edge's HTTP/3) and wireguard-go (the Edge and Outposts) ask for 7 MiB UDP buffers, which Linux caps at `net.core.rmem_max` and `net.core.wmem_max` (about 208 KiB by default), so packets drop under load. In system mode `install.sh` writes `/etc/sysctl.d/60-tnl.conf` with both set to 7500000 and applies it with `sysctl -p` before starting the unit. It prints a line saying what it set, keeps an existing file as it does `edge.env`, and only warns if applying fails. On an Outpost it does this only when the current limits are below 7500000. Compose has to set them on the Docker host, since a container cannot set `net.core.*`; the guide says so, and lists the file under uninstalling. No wire format or `state.json` change.
- **It stays out of** the firewall, port checks up front and uninstalling. If a unit fails to start, it prints the unit's last log lines. The docs list the ports, every step the script takes, and what to remove to uninstall.

### systemd units

Units are tnl's files. `install.sh` overwrites them on every run, and operators customise them with `systemctl edit` drop-ins. Both are `Type=simple`. If one ever becomes `Type=notify`, remember that `caddy.Load` sends `READY=1` itself.

```ini
# tnl-edge.service
[Unit]
Description=tnl Edge
Wants=network-online.target
After=network-online.target

[Service]
ExecStart=/usr/local/bin/tnl edge
EnvironmentFile=/etc/tnl/edge.env
Environment=XDG_CONFIG_HOME=/var/lib/tnl/config
DynamicUser=yes
User=tnl
StateDirectory=tnl
StateDirectoryMode=0700
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
Restart=on-failure
RestartSec=5s
RestartPreventExitStatus=78
TimeoutStopSec=20s

[Install]
WantedBy=multi-user.target
```

```ini
# tnl-outpost.service
[Unit]
Description=tnl Outpost
Wants=network-online.target
After=network-online.target

[Service]
ExecStart=/usr/local/bin/tnl connect
EnvironmentFile=/etc/tnl/outpost.env
Environment=TNL_STATE_DIR=/var/lib/tnl-outpost
DynamicUser=yes
User=tnl-outpost
StateDirectory=tnl-outpost
StateDirectoryMode=0700
CapabilityBoundingSet=
Restart=on-failure
RestartSec=5s
RestartPreventExitStatus=78

[Install]
WantedBy=multi-user.target
```

- **The token stays in `outpost.env`.** That's harmless: it works once, and a restart with it still set ignores it. To rekey, paste the new token into the file and restart.
- **No file limits are set,** because Go raises its own open-file limit to the hard limit.

### Images

- **Two images:** `ghcr.io/hyprsh/tnl` (full) and `ghcr.io/hyprsh/tnl-outpost`.
  - Both are built on `gcr.io/distroless/static-debian12:nonroot`, which provides uid 65532, the CA bundle and tzdata.
  - Both are multi-arch for linux/amd64 and linux/arm64, with `ENTRYPOINT ["tnl"]`.
- **The Edge image:** `CMD ["edge"]` and `TNL_STATE_DIR=/var/lib/tnl`.
- **The Outpost image:** `CMD ["connect"]` and `TNL_STATE_DIR=/var/lib/tnl-outpost`.
- **The state directory is owned by 65532 in the image,** so a named volume inherits that ownership. A bind mount needs `chown 65532`, and the docs say so.
- **No `VOLUME` and no `HEALTHCHECK`.**
- **Tags:** `X.Y.Z`, `X.Y`, `X` and `latest`.

The Compose examples show the declared setup ([Declared Zones and Outposts](#declared-zones-and-outposts)). They pin an exact `X.Y.Z`, take secrets from Compose's `secrets:`, give the Edge a named volume, and use `restart: unless-stopped` and the container names `tnl` and `tnl-outpost`:

```yaml
# The Edge
services:
  tnl:
    image: ghcr.io/hyprsh/tnl:X.Y.Z
    container_name: tnl
    restart: unless-stopped
    stop_grace_period: 20s
    environment:
      TNL_ADDRESS: edge.example.com
      TNL_KEY_FILE: /run/secrets/tnl-key
      TNL_ZONE_MAIN: example.com
      TNL_OUTPOST_NAS: nas 6WvT…=
    secrets: [tnl-key]
    ports: ["80:80/tcp", "443:443/tcp", "443:443/udp", "51820:51820/udp"]
    volumes: ["tnl:/var/lib/tnl"]
secrets:
  tnl-key:
    file: ./tnl-key
volumes:
  tnl:
```

```yaml
# An Outpost, on the Services' network
services:
  tnl-outpost:
    image: ghcr.io/hyprsh/tnl-outpost:X.Y.Z
    container_name: tnl-outpost
    restart: unless-stopped
    environment:
      TNL_CREDENTIAL_FILE: /run/secrets/tnl-credential
      TNL_ROUTE_PHOTOS: photos.example.com http://immich:2283
    secrets: [tnl-credential]
    networks: [apps]
secrets:
  tnl-credential:
    file: ./tnl-credential
networks:
  apps:
    external: true
```

- **The Edge publishes its ports** rather than using host networking, because on a bridge network Docker lets a non-root process bind ports below 1024. The docs carry one gotcha: without Docker's IPv6 enabled, IPv6 Visitors arrive through the userland proxy and lose their address.
- **Secret files are bind-mounted as they are on the host,** so each must be readable by uid 65532. The docs say so.
- **`outposts.md` keeps the token flow:** `TNL_TOKEN` in place of the credential, and a named volume for `/var/lib/tnl-outpost`.
- **The Outpost reaches Services by container name.** The docs warn that `localhost` inside the container isn't the host.
- **Running commands:** `sudo tnl …` on a host, `docker exec tnl tnl …` in a container. The image's `TNL_STATE_DIR` carries over into the exec.

### State directories and sockets

- **An Edge and an Outpost on one host never collide:**
  - the Edge's state directory is `/var/lib/tnl`
  - an Outpost under systemd or Docker uses `/var/lib/tnl-outpost`
  - any other Outpost uses `~/.local/state/tnl-outpost`
- **The CLI picks one socket:**
  1. If `--state-dir` or `TNL_STATE_DIR` is set, it uses only that directory.
  2. Otherwise it checks the user's Outpost directory, then `/var/lib/tnl-outpost`, then `/var/lib/tnl`, and uses the one live socket.
  3. If more than one is live, it refuses, lists them, and asks for `--state-dir`.
  4. If a socket exists but can't be opened, it says "run with sudo".

### Releases

- **Each `vX.Y.Z` tag triggers GoReleaser in GitHub Actions.** Only a plain `vX.Y.Z` does: a pre-release tag such as `v1.2.3-rc.1` triggers nothing, and the image script refuses it, so none can move `X.Y`, `X` or `latest`. It publishes to GitHub Releases:
  - one archive per build and platform, holding `tnl`, `LICENSE`, `NOTICE`, a README, and `systemd/tnl-edge.service` and `systemd/tnl-outpost.service`
  - `SHA256SUMS`
  - `install.sh`

  It also publishes both images.
- **Every archive and image gets a GitHub artifact attestation,** checked with `gh attestation verify`. The checksums only catch a corrupted download, so the attestations are the proof of origin. There are no GPG or minisign keys.
- **There is no `tnl upgrade` and no self-updater.**
- **Release notes:**
  - They open with the compatibility line.
  - A major's notes lead with an "Upgrading from 1.x" section.
  - Any release that migrates a state file says so.
- **Upgrading:** the Edge first, then each Outpost whenever convenient. At a major this order is required. The Upgrading page says that the `1` tag (`0.3` before 1.0) is safe for Outposts, and that `latest` and a bare `0` are not.
- **`tnl outpost add` and `rekey` print install lines (Linux and macOS) pinned to the Edge's version.**

- **Markdown in the repo, with no site generator:** `README.md` holds the quick start, and everything else is in `docs/guide/`.
- **systemd with `install.sh` leads for both roles,** and Docker Compose follows as a section of its own, equally supported.

| 250 MB, 20 s | the upload size and SSE heartbeat tnl must carry | [the map][map] |

## 11. Testing

- **One in-process harness, built in slice 1 and extended by every slice.**
  - An Edge, its Outposts and Services run in one `go test` process, with real WireGuard over loopback UDP.
  - Anything that obtains a certificate uses Pebble, with validation switched off (`PEBBLE_VA_ALWAYS_VALID=1`).
  - The wildcard path uses a fake DNS provider compiled into tests only.
- **The Caddy suite runs on every CI run,** in-process with timeouts shrunk to 2 s, as in the [timeouts research][t10]. It checks:
  - that nothing buffers an event
  - that SSE streams aren't cut, and survive reloads, on HTTP/1.1, HTTP/2 and HTTP/3
  - a 250 MB upload, and an upload whose Service stalls
  - background renewal of Route Hostnames
  - the certificate events

  Caddy is pinned exactly in `go.mod` and upgraded only in a PR of its own, so every upgrade passes the suite.
- **CI fails if the Outpost-only build links Caddy.**
- **CI runs real Edge and Outpost processes of different versions against each other** (`scripts/check-skew.sh`, run by `scripts/check.sh`). Inside the window everything must work. Outside it (a new 0.x minor) the Outpost must show as Incompatible. From 2.0, CI also runs against the last 1.x Outpost.
  - **Until a release exists,** the other version is the current tree built again with another version stamped into `main.version`: 0.1.0, 0.1.9 and 0.2.0. A same-minor pair must serve a Route, with the Edge on either side. A different-minor pair joins at the same minor, then one side is upgraded: the Outpost must answer 503 to Visitors, have its API calls refused and be logged by the Edge as incompatible, whichever side was upgraded. A pair that already differs cannot join, as a token is refused, so the check cannot start there.
  - **Once a plain `vX.Y.Z` tag exists,** the latest one is built from its own source (`git archive`, so no published archive is needed) and run against the current tree stamped as the tag's next patch, in both directions. With no tag that leg prints a notice and is skipped, so it switches on by itself after the first release. CI checks out with `fetch-depth: 0` to see the tags.
  - **The Edge runs on high ports without a public setting:** a build for the check is linked with `-X main.testWebFile=PATH`, and an Edge built that way reads its listen addresses, ports and test CA with its roots from that JSON file. A release build never sets it. A tag whose source lacks the hook runs only its Outpost, with a notice.
- **The browser check** happens once, by hand, in the [Reconnects](#6-reconnects) slice: Firefox, Chromium and Safari, with an Outpost stopped mid-stream. It was done on 2026-10-17 (#64), and the result is in ADR 0007 and [What Visitors see](#what-visitors-see-when-the-edge-answers): every browser retries, so there is no fallback.
- **Real-world conditions are covered by dogfooding,** not acceptance tests: a real VPS and NAT, Cloudflare, Let's Encrypt, browsers, streams held for hours, and whether a NAT accepts the Edge's first handshake after a restart.

## 12. Build order

- **Each slice ships as the next 0.x minor,** in the order slices land. 0.x minors needn't work together, so wire formats and `state.json`'s shape can still change.
- **Dogfooding starts** with the first release that includes [Reconnects](#6-reconnects). From then on, the operator's own Services run on tnl.
- **1.0.0 ships** once every slice is in, and the operator's Services have then run for 4 weeks without a change to a wire format or to `state.json`'s shape. A new API path that only `local` calls, on `tnl.sock`, is not a change to a wire format and does not restart the clock: the local socket links a CLI only with a process of the exact same version (the same-host rule of [Versions](#versions)), so no other version speaks the path. A path an Outpost or an Edge calls over the Tunnel still counts. That clock starts when [Status and `--json`](#10-status-and---json) ships.
- **Each slice writes the docs for what it adds,** and extends the harness.

```
1 Tracer bullet
├── 2 Release pipeline
├── 3 Joining ──────────► 4 Route management ──┐
├── 5 Zones and certificates ──────────────────┼──► 8 Declared Routes ──► 11 Declared Edge ──┐
├── 6 Reconnects ──┬───────────────────────────┘                                             │
│                  └──► 7 Version skew (also needs 3) ───────────────────────────────────────┼──► 10 Status and --json
└── 9 Backup ────────────────────────────────────────────────────────────────────────────────┘
```

Once slice 1 is in, slices 2, 3, 5, 6 and 9 can all run at once. Slice 11 lands before slice 10.
