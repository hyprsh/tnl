# Event-stream requests that would fail get `200` and `retry:`, not a reset

ADR 0007 had the Edge reset an event-stream request it would have answered with a 502 or 503, because an `EventSource` closes for good on a non-200 reply but retries a network error. Once an Outpost was Offline, some browsers retried that immediate reset several times a second, so every Visitor's browser kept the Edge busy and its log full. The Edge now answers such a request `200 text/event-stream` with the body `retry: 5000` and closes the stream at once. The browser keeps the stream as open-and-ended, reconnects, and waits 5 s before it does, so the rate is bounded by the `retry:` value and not by the browser. The real status still goes to the log, with `event_stream=true` on the line. The hand check of #64 showed that every browser also retries a reset, so retrying isn't the reason for the change; bounding the retry rate is. We chose this over a fallback to the status codes every other proxy sends, which still leaves each app to reopen its own `EventSource`. The cost is that `curl` sees a `200` where the Service is down, and that the Edge's answer hides the outage from anything that reads only the status. A stream cut mid-way, as when an Outpost's connection drops, still ends without a `retry:` field, and the Service's own `retry:` or the browser's default applies. This changes what Visitors see over HTTP, not a wire format or `state.json`, so the 1.0.0 clock does not restart.

See [docs/spec/v1.md](../spec/v1.md), What Visitors see when the Edge answers.
