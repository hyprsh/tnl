# Outposts manage their own Routes over the Tunnel

`tnl route` on an Outpost talks over a local Unix socket to the running `tnl connect`, which calls the Edge's API at `100.64.0.1` inside the Tunnel. The Edge takes the caller from the Tunnel source address, so an Outpost can change only Routes through itself, and its WireGuard key is its only credential. We chose this over cloudflared's split, where a separate `cert.pem` manages what the run token can't, and over a management API on public HTTPS with its own token. Whoever holds an Outpost's WireGuard key can already serve anything on that Outpost's Routes, so a second secret would add issuing, storing and rotating without shrinking that, and a public API would bring back the public endpoint and Edge Hostname that joining inside the Tunnel avoided. Unlike Pangolin, whose sites can push Routes for the whole org, an Outpost can't touch another Outpost's Routes; only the Edge host can. The cost is that Routes can be managed from an Outpost only while its Tunnel is up, a stolen WireGuard key also controls that Outpost's Routes, and on the Outpost's machine the socket's file permissions are the only gate.

See [Route management from the Outpost's CLI](https://github.com/hyprsh/tnl/issues/7).
