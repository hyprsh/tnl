# The Edge's state is one JSON file that only the running Edge writes

The Edge keeps everything it must remember in one `state.json` in its state directory: its WireGuard key, Outposts, Routes, and Zones with their DNS tokens. Caddy's certificate storage sits beside it in `caddy/`. The running Edge holds the state in memory and is its only writer. Every change takes one lock, whether it comes from the CLI on the Edge host, an Outpost over the Tunnel or a join. Under the lock the change is checked, written to a temp file, fsynced and renamed into place, and only then swapped in live. At every start the Edge builds its WireGuard peers, its Route table and Caddy's config from this file and its startup flags, so there is no second store to keep in sync, and Caddy's autosave and admin endpoint are switched off. We chose this over bbolt, SQLite and one file per object. The state is a few kilobytes, and bbolt and SQLite would add a dependency and an opaque file for strengths that don't apply here; the cgo SQLite driver would also break the plain `go build`. One file per object can't make `outpost rm --with-routes` or `zone rm --with-routes` atomic without a journal. The cost is that every change rewrites the whole file, and the file can't be edited while the Edge runs: the Edge refuses to save over an edit it didn't make. A hot copy of the directory isn't a safe backup either, because it can catch Caddy between writing a certificate's key and its certificate, so backups go through `tnl backup`.

See [Where the Edge keeps its state](https://github.com/hyprsh/tnl/issues/11).

Amended by [ADR 0010](0010-declared-outposts-connect-with-a-durable-credential.md) and [ADR 0011](0011-the-edge-may-declare-its-zones-and-outposts.md): the Edge's key may come from a file or a variable and must match the one in `state.json`, and the Edge's declared Zones and Outposts are saved in it.
